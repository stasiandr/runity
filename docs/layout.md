# Раскладка проекта: вид — по расширению, место — свободное

Карточка к решению DNA «Раскладка — по фичам, а не по типам» (2026-09-26).
Пересматривает пункт постулата 7 «Один стандарт на всё: структура папок
проекта».

## Решение автора (2026-09-26)

С opinionated в иерархии проекта мы перемудрили: всё лежит в папках по
типу, а так быть не должно. Реальные проекты бывают и плоскими, и
глубокими. Текстуру, материал, модель и префаб почти всегда выгодно
держать рядом. Код раскладывается по фичам, UI — по экранам и
компонентам.

Раскладка по умолчанию — схема Unreal (уточнение того же дня): корень
как у проекта Unreal (`Config/`, `Content/`, `Source/`), а внутри контента
— по стайлгайду Allar: папка проекта, `maps/`, `core/`, фичи,
`developers/`, сторонние паки рядом с папкой проекта.

## Что сейчас

Раскладка закреплена в `scrap-core/src/project.rs`. Это тринадцать папок
по типу: `scenes/`, `prefabs/`, `materials/`, `assets/`, `shaders/`, `ui/`,
`animators/`, `clips/`, `dialogues/`, `strings/`, `configs/`,
`src/components/`, `src/systems/`. Помидор из `examples/kitchen` лежит в
четырёх местах: `assets/kenney/food/tomato.glb`,
`materials/tomato.scrmat`, `prefabs/tomato.prefab` и код в
`src/components/` и `src/systems/cook.rs`. Добавить ингредиент — значит
пройти по четырём папкам, а удалить — не забыть ни одну из них.

Как движок сегодня находит файлы:

* **Ищет в своей папке, обычно на один уровень.** `Prefabs::open`,
  `Project::scene_names`, `MaterialShaders` (`shaders/`), `Motions::load`
  (`animators/`), экраны в studio, `build.rs` шаблона
  (`src/components/`, `src/systems/`). `sync` и `check` ходят по
  подпапкам (`scrap_import::walk`), рантайм и studio — нет. Поэтому
  префаб в `prefabs/food/` проходит `check`, но не грузится.
* **Ссылки уже не зависят от папки.** Библиотека собирается по ID
  (`library/<id>.scrasset`), у каждого файла-ассета есть сайдкар с ID,
  а модель, материал, префаб и звук в сцене — это `AssetLink` (имя плюс
  ID, docs/refs.md, этапы 1–3). Имя без ID находится, только если оно
  единственное в проекте, иначе `check` сообщает об ошибке.
* **Остались ссылки по имени, которые смотрят в конкретную папку.**
  `shader: "water"` — это `shaders/water.wgsl`. `animator: "door"` — это
  `animators/door.ron`. `start_scene` — это `scenes/<имя>.ron`. Шаблон
  игры читает `scenes/main.ron` и `ui/hud.ron` путями.
* **Раскладку сторожит `check_layout`,** и только в корне: незнакомый
  файл получает предупреждение и совет, в какую папку его перенести.
  `scrap rename` отказывается переносить префаб в подпапку.

Так что стены между папками держит поиск файлов, а не формат. Самая
трудная часть, ссылки по ID, уже сделана.

## Как это делают другие

* **Godot** в официальных best practices советует держать ассеты как
  можно ближе к сцене, которая их использует: `characters/player/`,
  `characters/enemies/goblin/`, `models/town/house/`. Сторонние
  плагины лежат в `addons/`. Движку место файла безразлично.
* **Unreal**, по стайлгайду Allar (стандарт де-факто): папки
  `Meshes/`, `Textures/`, `Materials/` дают «только избыточную
  информацию», потому что тип и так виден. Контент группируют по фичам
  (`Characters/`, `Weapons/`, `Effects/`), весь проект лежит в одной
  папке с его именем, общее ядро — в `Core/`. Карты собраны в одном
  `Maps/`, чтобы их проще было перечислить для сборки.
* **Unity** в своих рекомендациях описывает оба способа, по типу и по
  фичам. Для новичка советует по типу, а когда проект вырастет — переходить
  на фичи. Покупки из Asset Store лежат отдельно и в своей структуре: пак
  не разбирают по чужим папкам. На практике крупные Unity-проекты
  приходят к `_Project/Features/<фича>/` с кодом, префабами и
  материалами внутри.
* **Bevy** требует только `assets/` и что угодно внутри. Путь внутри —
  это и есть ссылка.
* **Код в индустрии** (веб, мобильная разработка, крупные Unity- и
  Unreal-проекты) раскладывают по фичам (вертикальные срезы): `cart/`,
  `checkout/`, `player/`. Папки `components/` и `systems/` на весь
  проект — это раскладка по типу, та же ошибка, что `textures/`.
* **UI** почти везде лежит так: `screens/` (или `pages/`) —
  экраны целиком, `components/` (или `widgets/`) — переиспользуемые
  куски, из которых экраны собраны.

Вывод: у всех, кроме «Unity для новичка», место файла выбирает человек, а
вид файла знают по расширению или типу. Движок, который требует папку,
учит плохой привычке и мешает вырасти.

## Модель

### Вид файла — по расширению, а не по папке

Движок один раз обходит проект и узнаёт вид каждого файла по его
расширению. Место файла ничего не значит.

| Вид | Расширение | Сейчас |
|---|---|---|
| сцена | `.scene.ron` | `scenes/*.ron` |
| префаб | `.prefab` | так же, но только в `prefabs/` |
| материал | `.scrmat` | так же, но только в `materials/` и `assets/` |
| модель, текстура, звук, шрифт | `.glb`, `.png`, `.wav`, … | только в `assets/` |
| шейдер | `.wgsl`, `.graph.ron`, `.vfx.ron` | только в `shaders/` |
| экран | `.screen.ron` | `ui/*.ron` |
| граф анимации | `.animator.ron` | `animators/*.ron` |
| клип | `.clip.ron` | `clips/*.ron` |
| диалог | `.dialogue.ron` | `dialogues/*.ron` |
| кейсы графа или диалога | `.cases.ron` | так же, рядом с графом |

Двойное расширение нужно из-за `.ron`. Сегодня RON — это и сцена, и
экран, и граф, и диалог, и различает их только папка. У нас уже есть
примеры такого приёма: `.graph.ron`, `.vfx.ron`, `.cases.ron`. Так делает
Unity (`.unity`, `.prefab`, `.mat`, `.controller`), и так же расширение
показывает тип в Unreal-префиксах (`SM_`, `M_`, `T_`). Двойное, а не
своё (`.scene`), затем, чтобы редакторы кода подсвечивали RON без
настройки.

Есть альтернатива: заголовок в файле (`// scrap: scene`) или поле
`kind`. Он хуже: вид файла не виден в `ls`, по нему нельзя написать
`.gitattributes`, и глоб агента `**/*.scene.ron` превращается в «открой
каждый `.ron` и посмотри».

Вид регистрирует модуль, который его приносит (решение «Голое ядро»):
ядро не знает слов «экран» и «диалог», оно знает таблицу «расширение →
вид» и позволяет модулям её пополнять.

### Индекс проекта

`Project::index` — один обход проекта: путь, вид, ID из сайдкара. Обход
пропускает `library/`, `target/`, `.git/`, папки на точку и `src/` (код
ищет `build.rs`, см. ниже). Все места, которые сейчас читают свою папку,
спрашивают индекс: префабы, список сцен, палитра материалов, шейдеры,
графы, экраны, пикеры, Project в studio, `check`, `scrap build`, MCP.
Индекс обновляется по тем же событиям файловой системы, по которым уже
перезагружаются ассеты: добавленный файл — строка в индексе, а не новый
обход.

Одна правда вместо двух обходов: рекурсивного у `sync` и `check` и
одноуровневого у рантайма. Уходит вся категория ошибок «`check`
видит, а игра нет».

### Ссылки — по ID; имя — только если оно единственное

Всё, что ещё ссылается по имени в папке, становится ссылкой (решение
«Всё, что может быть ссылкой, — ссылка»):

* `start_scene` в `scrap.ron` — это `SceneLink` (docs/refs.md, этап 4).
* `animator: "door"` — это `AssetLink` вида «граф анимации». Сайдкар с ID
  у графов уже есть.
* `shader: "water"` — имя, пока у шейдеров нет сайдкаров. Имя должно
  быть единственным в проекте, иначе `check` называет оба файла. Потом —
  ссылка, как у материала.
* Шаблон игры и код открывают сцену и экран ссылкой или по индексу
  (`project.scene("main")`), а не путём `scenes/main.ron`. Путь в коде
  остаётся допустимым: `data_file` работает с любым относительным
  путём, а `scrap build` сохраняет пути.

Имя без ID принимается, как сейчас, если оно единственное. Два
`rock.glb` в разных папках — нормально, пока сцена ссылается по ID, и
ошибка `check` только для строки без ID.

### Раскладка по умолчанию — схема Unreal

Движку место файла безразлично (вид — по расширению, ссылка — по ID).
Но у проекта есть раскладка по умолчанию: её пишет `scrap new`, по ней
лежат примеры, её описывает CLAUDE.md шаблона. Это схема Unreal: корень
проекта Unreal и стайлгайд Allar для контента.

```
kitchen/
  scrap.ron              проект                       ≈ Kitchen.uproject
  config/                настройки игры целиком       ≈ Config/
    input.ron            действия и клавиши           ≈ DefaultInput.ini
    layers.ron           слои столкновений            ≈ Collision в DefaultEngine.ini
  content/               всё, что делают художники,   ≈ Content/
                         дизайнеры и техдизайнеры
    kitchen/             папка проекта (Allar 2.2)
      maps/              все уровни (2.4)
      core/              то, на чём стоит игра (2.5): игрок, камера,
                         общие материалы, конфиг мира
      food/tomato/       фича: модель, текстура, материал, префаб рядом
      stations/stove/
      effects/
      ui/screens/        экраны
      ui/components/     куски экранов
    kenney/              сторонний пак как пришёл, с лицензией
    localization/        тексты, файл на язык         ≈ Content/Localization/
    developers/<имя>/    песочница (2.3): не едет в сборку
  src/                   код игры, по фичам           ≈ Source/<Project>/
  Cargo.toml  build.rs
  library/               производное, в .gitignore    ≈ DerivedDataCache/
  .scrap/                состояние редактора          ≈ Saved/
  CLAUDE.md
```

Что взято из Unreal и почему:

* **Корень: `config/`, `content/`, `src/`.** Настройки проекта, контент и
  код не перемешаны в одном корне с `Cargo.toml` и `library/`. Художнику
  нужна только `content/`, программисту — `src/`. `src/`, а не `source/`,
  потому что так ждёт cargo.
* **Папка проекта внутри `content/` (Allar 2.2).** Сторонний пак или
  модуль, распакованный в `content/`, ложится рядом с ней и ничего не
  смешивает: видно, что своё, а что чужое, и чужое обновляется целиком.
* **`maps/` — все уровни в одном месте (Allar 2.4).** Единственная
  «папка по типу», которую Allar оставляет: уровни — это точки входа, их
  перечисляют сборка, меню выбора уровня и человек. У нас сцена-уровень
  лежит в `maps/`, а сцена-кусок (комната, собранная для префаба) может
  лежать в фиче.
* **`core/` (Allar 2.5).** Сигнал «не трогай походя». Здесь лежит то, от
  чего зависит всё остальное.
* **`developers/<имя>/` (Allar 2.3).** Песочница, в которой не страшно
  мусорить. `scrap build` её не везёт. `check` называет ссылку из
  остального контента в `developers/`: такой ассет надо сначала
  перенести в фичу.
* **Фичи без папок по типу (Allar 2.6).** Никаких `meshes/`, `textures/`,
  `materials/` внутри фичи.

Что не взято:

* **Префиксы имён (`SM_`, `T_`, `M_`).** В Unreal они нужны, потому что
  все ассеты — `.uasset` и тип по имени файла не виден. У нас тип виден
  по расширению (`tomato.scrmat`, `tomato.prefab`), а имя без префикса
  короче в сцене и в диффе.
* **PascalCase.** Имена — snake_case, как в Godot: регистр файлов на
  macOS и Windows не различается, а имя файла — это имя в сцене и имя
  компонента в коде.
* **`Public/`/`Private/` в коде.** Это нужно из-за заголовков C++. В Rust
  видимость задаёт `pub`.

Что движок требует на самом деле: `scrap.ron` в корне, `config/input.ron`
и `config/layers.ron` (одни на игру; их читают код движка и `check`),
`content/localization/` (таблица на язык), крейт игры и `library/`.
Остальное — умолчание: проект, разложенный иначе, работает так же.
`check_layout` меняет смысл: он больше не требует папок, а называет файл,
вид которого движок не знает (например, `.ron` без двойного расширения),
и советует расширение.

### Конфиги — там, где их читает код

`Tuned` и `Table` грузятся путём из кода игры, и игра сама пишет, какие
таблицы читает и откуда (`library/tables.ron`, `TableShape.path`). Окно
Configs и `check` берут список из этого файла, а не из папки `configs/`.
Таблица рецептов лежит в `content/kitchen/food/recipes/`, рядом с едой,
как DataTable в Unreal лежит в контенте. Общие числа игры — в `core/`.
Отдельной папки `configs/` в раскладке по умолчанию нет.

### Код — по фичам

`build.rs` обходит весь `src/`, а не две папки:

* **Компонент** — файл, который объявляет `pub struct` с именем
  файла в PascalCase (`pot.rs` → `pub struct Pot`). Имя в сцене, как
  и сейчас, — имя файла (`"pot"`).
* **Система** — файл с `pub fn run(`.
* Остальные файлы — обычные модули игры, `build.rs` их не трогает.
* Два компонента с одним именем в разных папках — это ошибка сборки,
  и `build.rs` называет оба пути: сцена не смогла бы их различить.

Сгенерированные модули остаются плоскими (`components::pot`,
`systems::cook`), поэтому перенос файла между папками фич не ломает ни
`step`, ни сцены. Цена: такой файл нельзя ещё раз объявить через `mod`
в `mod.rs` фичи, его подключает `build.rs`. Об этом скажет CLAUDE.md
шаблона, а двойное объявление даст ошибку компилятора, так что тихо это
не сломается.

Проверка по тексту файла — тот же приём, которым `build.rs` сегодня
узнаёт `Serialize` и `NETWORKED`. Proc-macro-атрибут (`#[component]`)
был бы строже, но это ещё один крейт в сборке игры (постулат 1). Если
текстовая проверка начнёт ошибаться, вернёмся к нему.

### UI — экраны и компоненты

Экран — `.screen.ron` в любой папке. Раскладка по умолчанию кладёт
экраны в `content/<проект>/ui/screens/`, а общие куски — в
`ui/components/` (в Unreal так же разделяют экраны и виджеты UMG). Но переиспользуемых кусков у экрана
сейчас нет: элемент — текст, кнопка или картинка, и карточки заказов в
kitchen рисует код. «Экран ставит компонент, как сцена ставит префаб»
(`kind: Use(("order_card", "…"))` с переопределениями) — отдельная фича
для docs/ui.md. Раскладка ей не мешает, но и не делает её за неё.

остаётся целым и обновляемым. Своя модель, сделанная в Blender для этой
игры, легла бы в `food/tomato/` рядом с материалом.

## Ответы постулатам

1. **Скорость итерации.** Один обход вместо десятка, и индекс обновляется
   по событиям файловой системы. Бюджет: индекс проекта на 3000 файлов
   строится за время, которое держит тест, рядом с бюджетом `sync`. Код
   по фичам не меняет сборку: `build.rs` так же генерирует плоские
   модули, только обходит больше файлов, а это микросекунды.
2. **Git.** Переезд файла — это `git mv` его самого и сайдкара: ссылки по
   ID его переживают, сцены не меняются. `.gitattributes` пишется по
   расширениям (`*.scene.ron merge=scrap`, `*.prefab merge=scrap`), а не
   по папкам, так что merge driver работает где угодно. Всё, что
   относится к фиче, приходит одним каталогом в одном коммите, и ревьюер
   видит фичу целиком.
3. **Модульность.** Это прямо то, что нужно ассет-стору: модуль приносит
   свою папку как есть (код, префабы, материалы, текстуры рядом), и
   движку не нужно раскладывать её по шести чужим папкам. Контент модуля
   ложится в `content/<модуль>/` рядом с папкой проекта, как пак из
   Fab/Marketplace в Unreal. Виды файлов регистрируют модули, ядро знает
   только таблицу расширений. Где лежит код модуля, решает
   docs/modules.md («Модуль — исходник»).
4. **Сеть.** Ничего: `Spawn` называет префаб по ID.
5. **AI.** Агенту не надо гадать и сейчас: «все префабы» — это
   `**/*.prefab`, так же просто, как `prefabs/*`. MCP-инструмент
   `assets` и `scrap assets` перечисляют всё по видам с путями. CLAUDE.md
   шаблона говорит «ищи по расширению» и объясняет, где что принято
   класть. А раскладка по фичам даёт агенту контекст: открыв
   `food/tomato/`, он видит всё, что относится к помидору.
6. **Производительность.** В кадре ничего, всё происходит при открытии
   проекта и при изменении файлов.
7. **Opinionated.** Стандарт остаётся, но он о другом: закреплено, **как
   файл говорит, что он такое** (расширение) и **как на него ссылаются**
   (ID плюс имя), и что лежит в корне. Раскладка по умолчанию —
   схема Unreal, её пишет генератор, и по ней лежат примеры. Проект,
   разложенный иначе, работает так же. Это пересмотр пункта постулата
   «структура папок закреплена», сделанный явно (см. «Нарушения»). На
   вопрос постулата «с этим согласятся 90% игр?» ответ «да» именно для
   свободного места: раскладку по типу крупные проекты на Unity и Unreal
   бросают, когда вырастают.
8. **Батарейки.** Шаблон с хорошей раскладкой, `check`, который называет
   непонятный файл, и `scrap migrate-layout`, который переименовывает
   старые `.ron` по их папке.

## Нарушения и риски

* **Постулат 7 пересматривается явно.** Раньше в нём было: «Один стандарт
  на всё: структура папок проекта… закреплена». Теперь: «один стандарт
  того, как файл называет свой вид и как на него ссылаются; место —
  свободное, корень — закреплён». Аргумент прежней версии («проект,
  передвинувший `scenes/` куда-то хитро, — это проект, который следующий
  инструмент поймёт неправильно») отпадает: инструмент больше не ищет
  `scenes/`, он ищет `.scene.ron`.
* **Миграция форматов.** Каждый `.ron` сцены, экрана, графа, клипа и
  диалога получает двойное расширение. Нужны `scrap migrate-layout`
  (переименование по старой папке, сайдкары едут вместе) и период, когда
  `.ron` в старой папке читается как раньше и `check` предупреждает. По
  постулату 7 («вторая реализация — с датой удаления первой») старое
  чтение удаляется через месяц после миграции примеров, **2026-10-31**.
* **Ссылки по имени, которые остаются** (компоненты по имени файла,
  шейдеры до сайдкаров), становятся глобальными: два `door.rs` в разных
  фичах дают ошибку. Это правильно (сцена их не различит), но об этом
  нужно сказать словами и с обоими путями.
* **Обход всего проекта** наткнётся на большие чужие папки (`node_modules/`,
  выгрузки DCC). Индекс пропускает папки на точку и уважает
  `.gitignore`: что git не видит, того нет и в проекте.
* **Stem с двойным расширением.** У `main.scene.ron` stem — `main.scene`.
  Имя ассета должно браться одной функцией ядра (`kind_and_name(path)`),
  а не через `file_stem` в двадцати местах.

## Этапы

1. **Индекс.** `Project::index` и таблица расширений, которую пополняют
   модули. Все обходы из «Что сейчас» переходят на индекс, и те, что
   сегодня видят только верхний уровень, тоже. Файлы остаются где
   лежат: это рефакторинг без смены форматов. Тест: префаб, сцена, граф,
   экран и шейдер в подпапках находятся рантаймом, studio и `check`
   одинаково.
2. **Двойные расширения.** `.scene.ron`, `.screen.ron`, `.animator.ron`,
   `.clip.ron`, `.dialogue.ron`. Старые пути читаются до 2026-10-31,
   `scrap migrate-layout` переименовывает, `.gitattributes` в шаблоне по
   расширениям.
3. **Остальные ссылки.** `start_scene` и `animator` — `AssetLink`,
   шейдер — имя, уникальное в проекте, шаблон игры — без путей
   `scenes/…` и `ui/…`.
4. **Код по фичам.** `build.rs` обходит `src/`, `scrap add component
   cooking/pot` пишет файл в фичу, `Project::component_names` — из того же
   обхода.
5. **Шаблон и примеры.** `scrap new` пишет раскладку по умолчанию
   (схема Unreal): `config/`, `content/<проект>/maps|core|фичи`,
   `content/localization/`, `content/developers/`. `scrap build` не везёт
   `developers/`, `check` называет ссылку туда. `examples/kitchen` и
   `examples/valley` переезжают по этой схеме,
   CLAUDE.md шаблона и stack.md («Проект») переписываются.
   `check_layout` называет файлы непонятного вида, а не «не в той папке».
6. **Компоненты экрана.** Отдельной карточкой в docs/ui.md.
