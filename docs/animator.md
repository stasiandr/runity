# Аниматор: правила вместо графа

Статус: **предложение**, из обсуждения 2026-09-26. Не решение и не план
работ: сначала прототип и замер на Даче (см. «Этапы»).

Граф аниматора ругают во всех движках. Наш граф (`scrap::animgraph`,
[stack.md](stack.md), [animation.md](animation.md)) — Animator Controller
из Unity, записанный текстом. Текст, `check`, `.cases.ron` и след
переходов лечат симптомы, но модель остаётся той же, и её боли остаются:

1. **Взрыв переходов.** N состояний — до N² стрелок. Any State — костыль,
   с которым непонятно, кто кого перебивает.
2. **Поведение в скрытых полях стрелки.** Exit time, длительность,
   источник прерывания — на графе этого не видно.
3. **Два автомата.** У геймплея свой автомат (на земле, в прыжке,
   атакует), у аниматора — его копия, хуже. Связь — строки параметров.
   Отсюда «почему персонаж в этом состоянии»: две машины разъехались.
4. **Результат зависит от пути.** Состояние — следствие истории переходов,
   а не текущих параметров. Трудно отлаживать и трудно догнать по сети.
5. **Разовое действие — узел со стрелками туда и обратно.** Удар, эмоция,
   «подобрать» раздувают граф.

Ни Unity, ни Unreal, ни Godot эту модель целиком не починили, но у каждого
есть кусок решения. Берём лучшее и собираем свою модель из трёх частей.

## Модель

Аниматор персонажа — три вещи, у каждой своя простая модель:

| Часть | Что решает | Модель | Откуда |
|---|---|---|---|
| **Движение** | как идти с этой скоростью и в этом направлении | непрерывная функция параметров: blend 1D, потом 2D, потом motion matching | Unity Blend Tree, Unreal Blend Space / Motion Matching |
| **Режим** | что тело делает сейчас: стоит, падает, присел, мёртв | список правил по приоритету, первое подходящее | Unreal Chooser Table, Godot Transition |
| **Действие** | разовое: удар, эмоция, перезарядка | запускается кодом, играет в слоте поверх позы | Unreal Montage + Slot, Godot OneShot |

### Режимы — правила, а не стрелки

```ron
(
    params: { speed: Float, grounded: Bool, crouch: Bool, dead: Bool },
    modes: [
        (name: "dead",   when: "dead",                 play: "death", hold: true),
        (name: "fall",   when: "!grounded",            play: "fall", enter_after: 0.1),
        (name: "crouch", when: "crouch",               play: "crouch_move"),
        (name: "move",   when: "true",                 play: "locomotion"),
    ],
    blends: (
        default: 0.2,
        pairs: [
            (from: "fall", to: "move", via: "land", time: 0.1),
            (from: "*",    to: "dead", time: 0.05),
        ],
    ),
    motions: {
        "locomotion":  (blend_by: "speed", blend: [(0.0, "idle"), (1.6, "walk"), (4.0, "run")]),
        "crouch_move": (blend_by: "speed", blend: [(0.0, "crouch_idle"), (1.2, "crouch_walk")]),
    },
    sync: { "feet": ["locomotion", "crouch_move"] },
)
```

* **Каждый шаг правила проверяются сверху вниз, выигрывает первое
  подходящее.** Режим — функция текущих параметров, а не пути. N правил
  вместо N² стрелок. Приоритет виден глазами: выше — главнее.
* **Переход — это смена выбранного правила.** По умолчанию кроссфейд
  `blends.default`. Особые пары описаны отдельно: своя длительность,
  промежуточный клип `via` (приземление). Отдельный список пар вместо
  полей на каждой стрелке — боль 2.
* **Условия — выражения** (как `advance_expression` в Godot): `!grounded`,
  `speed > 0.1 && !crouch`. Параметры объявлены в `params` с типом, и
  `check` называет незнакомый параметр с ближайшим именем — и в файле, и в
  вызовах из игры. Магическая строка становится проверенным именем.
* **Против дребезга на порогах** правило может потребовать, чтобы условие
  держалось `enter_after` секунд (кочка не включает падение). `hold: true`
  — режим, из которого правила не выводят (смерть; выйти можно только
  явно из кода). Это единственное «состояние» режимов: таймеры в
  фиксированном шаге, детерминированные.
* **Sync-группы** (из Unreal): клипы одной группы идут в общей фазе и
  после смены режима. Левая нога ходьбы переходит в левую ногу ходьбы
  вприсядку. Сейчас фаза общая только внутри одного blend-состояния.
* **Правило играет motion, а не только клип.** `play` называет клип или
  запись из `motions` (blend 1D, потом 2D, потом motion matching). Движение
  не размазано по режимам.

### Действия — из кода, в слот

```ron
    actions: {
        "attack1": (clip: "slash_a", slot: "upper", blend_in: 0.1, blend_out: 0.2,
                    events: [(0.35, "hit")],
                    chain: [(on: "attack", window: (0.4, 0.8), to: "attack2")]),
        "attack2": (clip: "slash_b", slot: "upper", events: [(0.3, "hit")]),
        "wave":    (clip: "wave", slot: "upper"),
    },
    slots: { "upper": (mask: ["Spine"]), "full": (mask: []) },
```

* Игра говорит `controller.play("attack1")` и получает `ActionId`: события
  (`fired()`, как сейчас), «доиграл», «прервано». Игра, у которой уже есть
  свой автомат, говорит, *что делать*, а не ставит флаг в надежде, что
  граф поймёт. Это пересматривает правило stack.md «игра никогда не
  говорит „включи ходьбу“»: для режимов оно остаётся (режим выбирают
  правила), для действий отменяется.
* **Слот — это слой с маской** из [animation.md](animation.md). Слои и
  маски уже есть, действие просто занимает слой на время клипа.
* **Комбо — граф внутри действия** (`chain`): окно ввода, в котором
  повторное нажатие переводит в следующее действие. Граф нужен там, где он
  действительно граф, и живёт локально, а не во всём аниматоре.
* Действие в слоте `full` перекрывает режим целиком (кувырок). Режим под
  ним продолжает выбираться, так что после кувырка тело сразу в правильном
  режиме.

### Отладка — перемотка, а не подсветка

Из Rewind Debugger в Unreal. Аниматор каждый шаг пишет в отчёт игры
кольцевой буфер (последние ~10 с): выбранное правило, **почему не
сработали правила выше** (`#1 dead: false; #2 fall: !grounded = false`),
веса motion, занятые слоты, события. Окно Animator показывает шкалу
времени, и её можно перематывать. Агент получает то же текстом через
MCP-инструмент `why(entity, step)`.

Это отвечает на главный вопрос «почему персонаж в этом состоянии»
буквально: строкой, со значениями параметров.

## Чего не берём и почему

* **Граф состояний как основу** (Unity, Godot StateMachine, автомат в
  Unreal). Причины — все пять болей выше. Граф остаётся только внутри
  действия (`chain`).
* **`travel()` из Godot** (поиск пути по графу к цели). Хорошая идея для
  графа, но графа нет. Если комбо разрастутся, это кандидат для `chain`.
* **Произвольный граф поз как у AnimGraph в Unreal** (узлы blend, IK,
  cached pose). Сила Unreal, но это отдельный визуальный язык (постулат 7:
  одна правда). Порядок у нас фиксирован: режим → движение → слоты
  действий → слои → IK ([animation.md](animation.md)). Если фиксированного
  порядка не хватит, это следующая карточка.
* **Linked Anim Layers / Override Controller.** Набор клипов под оружие
  решается заменой имён клипов (`clips: { "idle": "rifle_idle" }` у
  строки сцены), а не подменой куска графа. Отдельный шаг, если
  понадобится.
* **Вложенных автоматов.** Та же причина, что в
  [animation.md](animation.md).

## Ответы постулатам

1. **Скорость итерации.** Файл аниматора — данные, `Tuned` перечитывает
   его на ходу, как граф сейчас. Правки правил, пар, действий видны на
   следующем шаге без перезапуска. Выражения разбираются при загрузке, а не
   компилируются вместе с игрой.
2. **Git.** Одно правило — одна строка, одно действие — одна запись.
   Добавить правило — вставить строку. **Слабое место:** приоритет — это
   порядок, и двое, переставившие правила в одном месте, получат конфликт.
   Это честный конфликт (два мнения о приоритете), и он виден в диффе
   одной строкой. Точечная запись (`ron_edit`) сохраняет комментарии, как
   сейчас.
3. **Модульность.** Всё это — модуль `animation`, замена `animgraph` внутри
   него. Шов для игры тот же: параметры и `play`. Можно отключить и
   анимировать своим кодом через `Animator` напрямую.
4. **Сеть.** Режим — функция параметров, а параметры реплицируются.
   Реплика и подключившийся посреди игры сразу получают правильный режим,
   без истории переходов: граф пришлось бы догонять по пути. **Триггер
   на один шаг** сервер (кэш последних значений) может потерять. Поэтому
   действия идут по сети как `(имя, шаг старта)` в сетевом компоненте
   аниматора: реплика и новичок запускают удар в той же фазе. Таймеры
   `enter_after` локальные, у реплики режим может смениться на шаг-два
   позже. Это видно только на кочках и допустимо. Владелец сущности —
   тот, кто ставит параметры и запускает действия, как с любым
   компонентом.
5. **AI.** Правда — текст. Раскладки нет: это таблица, её и рисовать не
   надо. Проверки громкие: параметр, клип, слот, режим в `pairs`, которых
   нет, называются с ближайшим именем. Недостижимое правило (выше стоит
   `when: "true"`) — ошибка `check`. `.cases.ron` остаются: шаг говорит,
   какие параметры и какой ожидается режим и слот. `why` объясняет любой
   шаг текстом.
6. **Производительность.** Правила — байткод выражений, 4–10 правил на
   персонажа за шаг, микросекунды. Дорогое — это выборка клипов, а её
   столько же, сколько сейчас. **Бюджет и кривая 10/100/1000 обязательны
   до замены графа.** Сейчас их нет и у слоёв (animation.md, нарушение
   6). Буфер перемотки — только в dev-сборке.
7. **Opinionated.** Одна модель: режимы, движение, действия. **Граф
   состояний уходит, а не живёт рядом**: двух официальных аниматоров
   параллельно не держим. Старые `animators/*.ron` читаются и
   переписываются в правила, как сейчас переписывается старый вид
   переходов. Где перевод неточен, там громкая ошибка с местом (см.
   «Открытые вопросы»).
8. **Батарейки.** Окно Animator становится таблицей правил: строки можно
   перетаскивать (приоритет), в игре подсвечено сработавшее правило, а
   проваленные условия выше него красные, со значениями. Плюс вкладка
   действий и шкала перемотки. Таблицу дизайнер поймёт быстрее графа:
   ни стрелок, ни раскладки.

## Открытые вопросы

Открытых вопросов DNA.md карточка не касается. Свои:

1. **Импорт Unity и порт Дачи — главный риск.** 105 Animator Controller
   Дачи приходят графом. Переходы из Any State переводятся в правила
   один в один. Переходы «из A в B при c» — нет: в графе состояние
   *держится*, пока не сработает исходящая стрелка, а правило
   пересчитывается каждый шаг. Варианты:
   (а) правило с `from: "A"` и `hold`: режим-«липучка», из которого
   выводят только правила с `from` — по сути стрелка, но только там, где
   она нужна;
   (б) импорт переводит, что может, и громко называет остальное, а
   остальное руками или агентом.
   Решаем по замеру: сколько из 105 — чистые blend/Any State, а сколько
   зависят от пути. Порт Дачи — приоритет, поэтому
   замена графа не должна его тормозить.
2. **`hold` и `from` возвращают граф через заднюю дверь.** Если импорт
   потребует их везде, модель проиграла. Критерий: в новом, не
   импортированном персонаже `from` не нужен.
3. **Выражения — свой маленький язык.** Нужен ли он, или хватит
   `(param, op, value)` из текущего графа, записанных строкой? Язык удобнее
   и знаком по Godot, но это ещё один парсер и ещё одни ошибки.
4. **Параметры, которые игра и так знает.** `grounded` и `speed` игра
   вычисляет и копирует в аниматор каждый шаг. Может, правило должно
   читать компонент напрямую (`when: "CharacterController.grounded"`)?
   Это убирает копирование и строки, но связывает анимацию с чужими
   модулями (постулат 3).

## Этапы

0. **Замер.** Прогнать 105 контроллеров Дачи: сколько переводятся в
   правила без `from`/`hold`. Сделать это до кода: от ответа зависит,
   жива ли карточка.
1. **Режимы.** `modes`, `blends`, `params` с `check`, чтение старого графа
   с переводом. Бюджет и кривая 10/100/1000.
2. **Действия.** `actions`, `slots` поверх слоёв, `play` → `ActionId`,
   `chain`. Сеть: `(имя, шаг)` в сетевом компоненте.
3. **Отладка.** Буфер перемотки, «почему не выше», `why` в MCP, шкала в
   окне.
4. **Окно.** Таблица правил вместо холста графа.
5. **Дальше.** Sync-группы между режимами, 2D-blend, motion matching как
   ещё один вид `motions`.
