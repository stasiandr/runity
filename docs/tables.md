# Таблица записей

Карточка к пункту 2 исследования «Инструменты геймдизайнеров и художников»
(`docs/history/2026-09-designer-tools-review/`).

Баланс делают в таблицах: все враги строками, здоровье и скорость
столбцами, поправил ячейку — посмотрел. Движки дают только формат записи
(ScriptableObject, DataTable, Resource), а таблицу к нему каждый
прикручивает сам: Odin Inspector, Scriptable Sheets, Google Sheets. Из
исследования же главная жалоба на DataTable в Unreal: правда — бинарный
`.uasset`, а реимпорт CSV затирает правки, сделанные в редакторе. Поэтому
у нас правда — RON-файлы в git, а таблица — вид на них.

## Что берём

1. **Таблица записей одного типа (Odin Table, Scriptable Sheets).**
   Строка — запись, столбец — поле, ячейка правится на месте, клик по
   заголовку сортирует.
2. **Ключ строки и структура (DataTable из Unreal).** Файл в `tuning/`,
   значение которого — словарь записей, — это таблица:

   ```ron
   {
       "goblin": (hp: 10, speed: 2.5),
       "orc": (hp: 30), // speed по умолчанию
   }
   ```

   Игра читает его как `Tuned<BTreeMap<String, Enemy>>`, перечитывает на
   ходу, как любой `tuning/`. Файл-структура (`tuning/world.ron`) —
   таблица из одной строки.
3. **Схема без кода игры в редакторе.** Игра говорит, как читает файл, там
   же, где регистрирует компоненты:
   `components.register_tuning::<BTreeMap<String, Enemy>>("enemies")`.
   `write_shapes` кладёт формы рядом с `library/components.ron` — в
   `library/tuning.ron`. Редактор и `check` читают формы оттуда и игру не
   линкуют. Пока игра не написала форму, столбцы — поля, которые пишут сами
   записи.
4. **Сущности сцены — тоже таблица.** Поиск как в Hierarchy (`c:enemy`,
   `p:campfire`): строка — сущность; с `c:<компонент>` столбцы — поля
   компонента, без него — имя, модель, материал, трансформ, слой.
5. **Проверка записей.** `scrap check` сверяет каждую запись с формой:
   лишнее поле с ближайшим похожим, не тот тип значения — с файлом и
   записью (`tuning/enemies.ron: record goblin: no field sped (did you mean
   speed?)`). То же видно в строке таблицы красным.

## Чего не берём и почему

* **Импорт из Google Sheets и CSV.** Вторая правда рядом с файлом — ровно
  то, за что ругают DataTable. Правда одна — RON в git (постулаты 2 и 7).
* **Файл на запись (ScriptableObject на каждого врага).** Запись в словаре
  — один блок, дифф правки — одна строка, разные записи сливаются git'ом
  без конфликта. Папку файлов сделать можно, но это второй способ того же.
* **Формулы и вычисляемые столбцы.** Это логика — она в коде игры
  (постулат 5).
* **Редакторы полей инспектора в ячейках.** Ячейка — текстовое поле с
  RON; пикеры, слайдеры и флажки — следующим этапом.

## Ответы постулатам

1. **Скорость итерации.** Ячейка файла `tuning/` пишется сразу, игра
   перечитывает файл через `Tuned::poll` (четверть секунды). Ячейка сцены
   — правка документа, запущенная игра видит её, как любую правку.
2. **Git.** Меняется только поле в тексте (`records::set` поверх
   `ron_edit`): комментарии, выравнивание и другие записи остаются байт в
   байт, пустая ячейка убирает поле из записи. Два человека, поменявшие
   разные записи, сливаются построчно; одну и ту же ячейку — обычный
   конфликт git в одной строке. Merge driver по записям для `tuning/` не
   сделан: у сцен он есть, у словарей записей пока нет.
3. **Модульность.** Таблица — панель редактора и функции сессии; движку и
   игре она ничего не стоит. Отдельным модулем не выделена: реестра панелей
   модулей ещё нет.
4. **Сеть.** Не касается: это время правки. Каждый участник читает свой
   `tuning/`; разные числа у хоста и гостя — не забота таблицы.
5. **AI.** `Session::table`, `set_cell`, `set_cells`, `undo_cell`; MCP —
   `table` (без аргумента — список таблиц), `set_cell`, `undo_cell`; файлы
   `tuning/` — ресурсы MCP. Ошибка — словами, с ближайшим именем записи
   или поля. Всё headless, тесты — в сессии, MCP и студии.
6. **Производительность.** В кадре игры ничего. Таблица строится из
   текста при открытии и после правки; тысячи строк не мерили.
7. **Opinionated.** Один формат таблицы — словарь записей в файле
   `tuning/`, одна правда — текст.
8. **Батарейки.** Дизайнер правит числа без программиста, но столбцы с
   типами появляются, когда программист добавил одну строку
   `register_tuning`; до того таблица показывает поля из текста.

## Где постулаты тянут

* **Ключ записи — имя, без ID.** Решение «Всё, что может быть ссылкой, —
  ссылка» (docs/refs.md, этап 5 «Конфиги») обещает записям конфигов ID. Тут
  ключ — только имя (`"goblin"`), как у слоёв и ключей строк сегодня.
  Ссылок на записи из сцен пока нет, так что переименование ничего не
  рвёт; ID для записей решит этап «Конфиги», а не эта карточка.
* **Своя отмена у `tuning/`.** Отмена сессии — снимки документа сцены, а
  файл `tuning/` пишется сразу. Поэтому у ячеек файла свой стек
  (`undo_cell`, кнопка Undo Cell): он не смешан с Ctrl+Z сцены и
  отказывается откатывать файл, изменённый после правки. Единая история
  правок сцены и файлов проекта — отдельная задача.

   файла, поле, правка одного поля на месте, проблемы по записям;
   `Components::register_tuning` и `library/tuning.ron`; шаблон игры
   регистрирует `world`; `check` называет запись и ближайшее поле;
   `Shape` проверяет словари.
2. Таблица в сессии и для агента. Сделано (2026-09-25): `table` из файла
   `tuning/` или поиска по сцене, `set_cell`/`set_cells` (сцена — один шаг
   отмены, файл — `undo_cell`), MCP `table`, `set_cell`, `undo_cell`,
   `tuning/` среди ресурсов.
3. Панель Table в студии. Сделано (2026-09-25): список таблиц и строка
   поиска, сетка текстовых полей, сортировка по столбцу, записи с
   проблемами красным, Undo Cell; Window › Table.
4. Редакторы полей инспектора в ячейках, выделение столбца и ввод во все
   ячейки сразу в окне (в сессии и MCP уже есть), добавление и удаление
   записи.
