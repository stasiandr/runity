# Как написать графический рендерер без зависимостей

Вопрос распадается на три независимые задачи, и путать их не стоит:

1. **Закрасить треугольники.** Растеризация — чистая арифметика: никакого
   «графического API» для неё в принципе не нужно. Нужен массив пикселей и
   краевые функции.
2. **Посчитать, какого цвета каждый пиксель.** Это отдельная задача и самая
   интересная: физически корректное освещение, отражения, тени. «Шейдеры» —
   это про неё, и к API она отношения не имеет вовсе.
3. **Показать результат на экране.** Вот здесь операционная система
   действительно нужна — и именно за этим обычно тянут `winit`/`sdl2`/`glfw`.
   Но окно можно попросить и самому: на macOS — через Objective-C runtime,
   который снаружи обычный C-API; на Linux — байтами в сокет; на Windows —
   пятью функциями из `user32.dll`.

Дальше — как сделано всё три в этом репозитории. И часть 6 — про то, что
рендерер, собственно, обслуживает: мир, который живёт сам по себе, одинаково
на любой машине и после загрузки сохранения.

## Часть 1. Растеризатор (`runity-render`)

GPU не делает никакой магии — он делает одно и то же для каждого треугольника,
просто очень параллельно. Повторить это на CPU — примерно 400 строк.

### 1.1. Вершинная стадия

Вершина умножается на матрицу `model-view-projection` и попадает в **clip
space** — однородные координаты `(x, y, z, w)`. Проекционная матрица здесь
правосторонняя, с глубиной в `[0, 1]` (соглашение Vulkan/D3D, а не OpenGL):
при нём ближняя плоскость — ровно `z == 0`, и отсечение сводится к одному
сравнению.

Шейдер — это трейт, а не строка с GLSL:

```rust
pub trait Shader {
    type Varying: Varying;                                  // что интерполируем
    fn vertex(&self, v: &Vertex) -> VertexOutput<Self::Varying>;
    fn fragment(&self, varying: &Self::Varying) -> Option<Color>;  // None = discard
}
```

От `Varying` нужны всего две операции — `scale` и `add`. Именно они и есть
контракт интерполятора в железе; всё остальное (цвет, нормаль, UV, любая
пользовательская структура) выражается через них.

### 1.2. Отсечение по ближней плоскости

Это единственное отсечение, которое обязано быть **до** деления на `w`. Если
треугольник пересекает плоскость камеры, у части вершин `w ≤ 0`, и после
деления геометрия «вывернется» на экран. Алгоритм Сазерленда — Ходжмана по
одной плоскости `z ≥ 0` даёт максимум 4 вершины, которые разбиваются веером на
треугольники.

Остальные пять плоскостей отсекать не нужно: за них отвечают ограничивающий
прямоугольник на экране и проверка диапазона глубины — дешевле и проще.

### 1.3. Растеризация: краевые функции

Для треугольника считаем знаковую площадь и три краевые функции:

```
e(a, b, p) = (b.x - a.x) * (p.y - a.y) - (b.y - a.y) * (p.x - a.x)
```

Пиксель внутри, если все три функции одного знака; поделив их на площадь,
сразу получаем барицентрические координаты. Отсечение задних граней — это
просто знак площади (после переворота оси Y лицевые CCW-треугольники дают
отрицательную площадь).

**Правило top-left.** Если пиксель попал ровно на общее ребро двух
треугольников, он должен достаться ровно одному из них — иначе на стыках либо
щели, либо двойной блендинг полупрозрачности. Тест
`fullscreen_quad_covers_every_pixel_exactly_once` проверяет это буквально:
два треугольника на весь экран должны дать ровно `width * height`
закрашенных фрагментов, ни одним больше.

### 1.4. Перспективная коррекция

Главная ошибка наивного софт-рендера — интерполировать UV линейно по экрану.
Линейна по экрану только `z/w`; всё остальное нужно интерполировать через
`1/w`:

```
1/w  = b₀·(1/w₀) + b₁·(1/w₁) + b₂·(1/w₂)
attr = (b₀·attr₀/w₀ + b₁·attr₁/w₁ + b₂·attr₂/w₂) / (1/w)
```

Проверяется это не «на глаз»: тест `interpolation_is_perspective_correct`
рендерит пол в перспективе, а потом для каждого закрашенного пикселя
независимо считает луч из камеры, пересекает его с плоскостью `y = 0` и
сравнивает полученные UV с тем, что записал растеризатор.

### 1.5. Буфер глубины

`Vec<f32>`, инициализированный `+∞`, тест `z < depth[i]`. Early-Z (тест до
вызова фрагментного шейдера) даёт заметную экономию, а запись глубины
происходит уже после — иначе `discard` во фрагментном шейдере оставлял бы
дырки в буфере.

## Часть 2. Как посчитать цвет (`runity-render`)

Растеризатор отвечает на вопрос «какие пиксели», шейдинг — на вопрос «какого
они цвета». Здесь и живёт почти всё, что делает картинку красивой.

### 2.1. Сначала — линейное пространство и HDR

Без этого дальше можно не начинать. Свет складывается и умножается линейно, а
sRGB — кривая: сумма двух значений в sRGB физически бессмысленна. Поэтому
фреймбуфер хранит **линейный float без верхней границы**, и клампинг случается
ровно один раз, в самом конце:

```
экспозиция → тонмаппинг (ACES) → sRGB → 8 бит
```

Именно «без верхней границы» делает возможным всё остальное: солнце может быть
в сто раз ярче белого, отражение может быть ярче поверхности, а bloom — это
буквально «то, что выше единицы». В 8-битном буфере ничего этого не существует.

Побочный эффект: текстуры-альбедо надо декодировать из sRGB в линейное при
загрузке, иначе всё освещение будет систематически неверным.

### 2.2. PBR: микрофасетная модель Кука — Торренса

Поверхность моделируется как поле микроскопических зеркал. Три множителя:
**D** — сколько зеркал смотрят в сторонуполувектора (GGX), **V** — сколько из них
затеняют друг друга (Smith, height-correlated), **F** — какая доля света
отражается под этим углом (Шлик). Диффуз получает ровно то, что не отразилось,
— отсюда сохранение энергии, которого у Блинна — Фонга с его отдельно
подкрученным `specular_strength` быть не может.

Проверяется это «печкой» (white furnace test): BRDF интегрируется по полусфере
и не должна вернуть больше света, чем пришло. Тест гоняет четыре шероховатости
на металле и диэлектрике — он ловит любой потерянный нормировочный множитель.

Workflow — metal/roughness: у диэлектриков F0 = 4%, у металлов F0 = собственный
цвет (поэтому у золота жёлтый блик, а у пластика белый), и у металлов нет
диффузной составляющей вовсе.

### 2.3. Отложенный рендеринг

Геометрический проход пишет в G-buffer: albedo, нормаль, позицию,
шероховатость, металличность. Освещение считается **один раз на пиксель**, уже
после. Две причины: стоимость освещения перестаёт зависеть от overdraw, и —
главное — screen-space эффекты получают то, без чего они невозможны: для
каждого пикселя известно, *какая там поверхность*.

### 2.4. Небо и IBL

Одного «ambient color» мало: свет сверху синий и яркий, снизу — тусклый и
тёплый, а зеркало должно отражать именно это, а не константу. Небо здесь
генерируется аналитически (градиент + солнце + дымка) и превращается в две
вещи:

* **девять коэффициентов сферических гармоник** — из них диффузная облучённость
  для любой нормали восстанавливается за двадцать умножений;
* **маленькую equirect-карту с мип-цепочкой**, где каждый уровень играет роль
  всё более шероховатого отражения.

Диск солнца в префильтрованную карту сознательно **не** запекается: на карте
128×64 он меньше текселя. Солнце — это направленный источник, и его блик куда
лучше рисует GGX-лепесток.

Тест, который ловит почти любую ошибку в этом коде: под равномерным небом
яркости L облучённость обязана быть ровно L с любой нормали.

### 2.5. Тени

Классический shadow mapping: сцена рендерится глубиной из точки зрения света,
при затенении спрашиваем — является ли эта точка ближайшим, что свет видит в
этом направлении. Две детали решают, как это выглядит: **смещение** (иначе
каждая освещённая поверхность затеняет сама себя полосами) и **фильтрация**
(PCF, девять отсчётов — иначе на границе получается лесенка). Отсечение
передних граней при рендере карты уводит артефакты самозатенения на обратную
сторону объектов.

Фильтр — фиксированный паттерн, а не повёрнутый случайный: golden-тесты требуют,
чтобы один и тот же пиксель разрешался одинаково в каждом прогоне.

### 2.6. SSAO

Небо освещает отовсюду — это верно в чистом поле и неверно в углу. SSAO
считает, какая доля полусферы над точкой заслонена тем, что есть в буфере
глубины, и умножает на это **только ambient**: у прямого света свои тени.

### 2.7. SSR

Карта окружения знает про небо и ничего не знает про объекты сцены, поэтому
полированный пол отражает небо, но не коробку, которая на нём стоит. SSR
марширует отражённым лучом по буферу глубины и, найдя пересечение, **заменяет**
вклад окружения на то, что нашёл (а не добавляет сверху: вклад окружения
известен точно, потому что его посчитал предыдущий проход).

Ограничение метода стоит проговорить честно, потому что оно видно: отразить
можно только то, что есть на экране. Всё, что за кадром или закрыто чем-то
другим, луч не найдёт — и отражение честно откатится на окружение.

### 2.8. Bloom и оптика

Bloom — это «то, что ярче белого, растекается по соседям», и он имеет смысл
только в HDR: в 8-битном буфере извлекать нечего. Извлечение с мягким коленом,
пирамида down/upsample, сложение обратно.

Дальше — вигнетка, зерно, хроматические аберрации, насыщенность и контраст. Всё
это работает в линейном пространстве, **до** тонмаппинга, потому что там «на 20%
темнее» означает 20% света.

### 2.9. Мип-маппинг и сглаживание

Шахматный пол под скользящим углом — худший случай для точечного сэмплинга:
соседние пиксели попадают в несвязанные тексели, и картинка «кипит». Текстуры
хранят мип-цепочку, а геометрический проход выбирает уровень по размеру пикселя
в мире (расстояние × угловой размер пикселя, делённое на наклон поверхности).
Дробные уровни смешиваются — трилинейная фильтрация.

Сглаживание — суперсэмплинг: рендер в N раз больше и усреднение. Важно, что
усреднение происходит **в линейном пространстве до тонмаппинга** — иначе края
получаются не чистыми, а просто серыми.

## Часть 3. Как показать кадр (`runity-platform`)

Основная целевая платформа — **macOS**; X11 и Win32 сделаны тем же способом и
живут рядом.

### 3.1. macOS: Objective-C runtime как C-API

На маке оконный сервер недоступен «по сокету», как X11: интерфейс — это
Objective-C. Но сам рантайм — обычная C-библиотека, и ровно её и вызывают
крейты `objc`/`cocoa`:

```rust
#[link(name = "objc", kind = "dylib")]
extern "C" {
    fn objc_getClass(name: *const c_char) -> Id;
    fn sel_registerName(name: *const c_char) -> Sel;
    fn objc_msgSend();
}
```

`[obj doThing:arg]` — это `objc_msgSend(obj, sel_registerName("doThing:"), arg)`.
Тонкость одна, но важная: **у `objc_msgSend` нет одной сигнатуры**. Его нужно
привести к той, которую ждёт конкретный селектор, иначе аргументы уедут не в те
регистры. Поэтому в бэкенде для каждой формы вызова есть свой типизированный
хелпер (`msg_id`, `msg_u64`, `msg_point`, `msg_window_init`, …).

Вторая тонкость — возврат структур. На x86_64 структура больше двух машинных
слов возвращается через скрытый указатель, и для этого есть отдельная точка
входа `objc_msgSend_stret`; на arm64 такого разделения нет. Поэтому `NSRect`
(4 × `CGFloat` = 32 байта) читается через `#[cfg(target_arch)]`, а `NSPoint`
(16 байт) — обычным `objc_msgSend` на обеих архитектурах.

**Вывод кадра — без подкласса `NSView`.** Content view делается
layer-backed (`setWantsLayer:YES`), и каждый `present` подсовывает слою свежий
`CGImage`:

```
CGDataProviderCreateWithData(pixels) → CGImageCreate(…, bitmapInfo, …) →
[CATransaction begin] → [layer setContents:image] → [CATransaction commit]
```

`bitmapInfo = kCGImageAlphaNoneSkipFirst | kCGBitmapByteOrder32Little` — это
ровно наш `0x00RRGGBB`, конвертация не нужна. Явная `CATransaction` нужна
потому, что мы не крутим главный run loop, а неявная транзакция коммитится
именно в нём.

Владение памятью: `CGImage` может пережить вызов `present` (слой его держит),
поэтому буфер пикселей не одалживается, а передаётся — `Box::into_raw` плюс
release-callback, который его освобождает ровно один раз.

**Ввод — без делегата.** `-[NSApplication nextEventMatchingMask:untilDate:...]`
с датой в прошлом — это неблокирующий опрос настоящей очереди событий:

```
loop {
    event = [NSApp nextEventMatchingMask:NSEventMaskAny
                               untilDate:[NSDate distantPast]
                                  inMode:NSDefaultRunLoopMode dequeue:YES];
    if (!event) break;
    // разобрать [event type], [event keyCode], [event locationInWindow]
    [NSApp sendEvent:event];   // без этого не работают перетаскивание и крестик
}
```

Грабли, которые стоит знать заранее:

* **Модификаторы не присылают key-события.** Cocoa шлёт `FlagsChanged` со всей
  маской, и нажатие/отпускание — это разница двух масок.
* **Начало координат снизу слева**, у нас — сверху слева, так что `y`
  переворачивается.
* **Закрытие окна и фокус** без делегата видны через само окно: `isVisible`
  и `isKeyWindow`. Заодно `setReleasedWhenClosed:NO` — иначе `NSWindow`
  освободит себя сам при закрытии, и наш указатель повиснет.
* **Autorelease pool на кадр** (`objc_autoreleasePoolPush/Pop`), иначе
  автоосвобождаемые объекты копятся всё время жизни процесса.
* **Только главный поток.** AppKit это требует; `open()` проверяет
  `[NSThread isMainThread]` и возвращает ошибку вместо падения.
* **`BOOL` — это `signed char`** на x86_64, и там бывают значения, отличные от
  0 и 1. Поэтому в FFI он `i8`, а не Rust `bool` (для которого это было бы UB).
* **Retina.** Слою выставлен `contentsScale = 1.0`: софтварный растеризатор не
  должен считать вчетверо больше фрагментов. HiDPI — отдельная задача.
* Приложению **не нужен `.app`-бандл**: `setActivationPolicy:Regular` +
  `activateIgnoringOtherApps:` делают бинарник из терминала полноценным окном.

Что проверяется без мака: чистая часть (таблица `kVK_*`-кодов, разбор масок
модификаторов, кнопки мыши, переворот `y`) вынесена в отдельный модуль и
тестируется на любой машине; раскладка `NSRect`/`NSPoint` и формат битмапа
покрыты тестами, которые гоняются на маке; сам FFI компилируется под обе
архитектуры (`cargo check --target aarch64-apple-darwin` и
`x86_64-apple-darwin`) в CI, а на раннере `macos-latest` он ещё и линкуется и
запускается.

### 3.2. Linux: X11 — это просто сокет

Ключевой факт, который экономит все зависимости: **X11 — сетевой протокол, а
не библиотека.** X-сервер владеет экраном, клавиатурой и мышью, приложения —
его клиенты, а `libX11` только сериализует структуры в сокет. `std` умеет
открывать сокеты, значит, всё нужное уже есть:

```rust
UnixStream::connect("/tmp/.X11-unix/X0")
```

Дальше — пять запросов, и окно на экране:

| Запрос | Opcode | Зачем |
| --- | --- | --- |
| setup (handshake) | — | версия протокола + cookie из `~/.Xauthority` |
| `CreateWindow` | 1 | завести окно |
| `ChangeProperty` | 18 | заголовок (`WM_NAME`, `_NET_WM_NAME`) и `WM_DELETE_WINDOW` |
| `CreateGC` | 55 | графический контекст |
| `MapWindow` | 8 | показать |
| `PutImage` | 72 | залить кадр |

Детали, на которых обычно спотыкаются:

* **Длина запроса измеряется в четвёрках байт**, а строки дополняются нулями
  до кратности четырём. Ошибся на байт — рассинхронизируется весь поток
  (именно так и провалился первый прогон теста в этом репозитории).
* **`PutImage` ограничен `maximum-request-length`** из ответа сервера (обычно
  256 КБ). Кадр 1920×1080 туда не влезает, поэтому он уходит горизонтальными
  полосами; `dst-y` у каждой полосы свой.
* **Формат пикселя.** При глубине 24 и 32 битах на пиксель сервер ждёт ровно
  тот `0x00RRGGBB`, который уже лежит в нашем фреймбуфере.
* **Клавиши.** X отдаёт *keycode* — номер физической клавиши, зависящий от
  железа и драйвера. Переносимое имя клавиши — *keysym*; таблицу отдаёт запрос
  `GetKeyboardMapping` (opcode 101). Хардкодить `keycode 25 == W` нельзя.
* **Закрытие окна** — не событие X, а сообщение оконного менеджера: нужно
  зарегистрировать атом `WM_DELETE_WINDOW` в свойстве `WM_PROTOCOLS` и ловить
  `ClientMessage`.
* **Неблокирующее чтение, блокирующая запись**: события читаются до
  `WouldBlock`, но на время записи кадра сокет возвращается в блокирующий
  режим — иначе `PutImage` может уйти наполовину.

Всё это проверяется без всякого дисплея: `tests/x11_wire.rs` поднимает
**поддельный X-сервер** на Unix-сокете, отвечает настоящими байтами протокола,
инжектит `KeyPress`/`ConfigureNotify`/`ClientMessage` и проверяет, что клиент
прислал корректные `CreateWindow`, заголовок и нарезанный на полосы `PutImage`.
`unsafe` в этом бэкенде нет вообще — это просто разбор байтов.

### 3.3. Windows: пять функций из `user32`

Сокета нет, зато можно объявить нужные функции самому — крейты `winapi`/
`windows` тоже делают только это:

```rust
#[link(name = "user32")]
extern "system" {
    fn RegisterClassW(class: *const WNDCLASSW) -> u16;
    fn CreateWindowExW(/* ... */) -> HWND;
    fn PeekMessageW(msg: *mut MSG, hwnd: HWND, min: u32, max: u32, remove: u32) -> i32;
    /* ... */
}
```

Кадр выводится через `StretchDIBits` с `BITMAPINFOHEADER`, у которого
`biHeight` **отрицательная** — это значит «строки сверху вниз», как в нашем
фреймбуфере, и `biBitCount = 32`, `biCompression = BI_RGB` — снова ровно наш
`0x00RRGGBB`.

### 3.4. Headless

Четвёртый бэкенд реализует тот же трейт `Window` поверх `Vec<u32>`. Он не
компромисс ради CI, а полноценная часть дизайна: движок целиком тестируется без
дисплея, а `RUNITY_HEADLESS=1` превращает любой пример в рендер скриншота.

## Часть 4. Отладка и headless-разработка

Это основной режим работы движка, а не побочный: кадр, посчитанный в память,
можно разобрать по слоям и сравнить с эталоном, ничего для этого не открывая.

### 4.1. Отладочные виды

`engine.debug_view` — один переключатель, который применяет главный цикл; код
игры о нём не знает:

* `Wireframe` — не линии поверх кадра, а **тот же конвейер**: фрагмент доживает
  до шейдера, только если он ближе `line_width` пикселей к ребру. Значит,
  каркас работает с любым шейдером и корректно тестируется по глубине.
  Расстояние до ребра берётся даром: краевая функция, делённая на длину ребра,
  и есть расстояние в пикселях.
* `Depth` — буфер глубины в градациях серого, нормированный по содержимому
  кадра. Без нормировки смотреть не на что: перспективная глубина тратит почти
  весь диапазон у самой камеры.
* `Overdraw` — счётчик записей в пиксель, тепловой картой. Счётчик включается
  только вместе с этим видом: он стоит аллокации и одной ветки на записанный
  фрагмент.
* `Albedo`, `Normals`, `Material`, `Occlusion` — содержимое G-buffer'а и
  результат SSAO по отдельности. Когда картинка выглядит неправильно, первый
  вопрос всегда «какой из буферов врёт», и это ответ на него.

Поверх — `draw_normals`, `draw_axes`, `draw_wireframe`. Они игнорируют глубину
и отсекают отрезки по границам вьюпорта (Лианг — Барски), иначе линия, уходящая
за экран, стоила бы миллион шагов Брезенхэма.

### 4.2. Golden-тесты

Вопрос «изменилась ли картинка» на машине без дисплея решается сравнением
пикселей:

```rust
golden::assert_matches("tests/golden/scene.png", &frame, Tolerance::new(4, 0.02));
```

Что здесь важно:

* **Допуск обязателен.** Побитового совпадения между архитектурами не бывает:
  `sin`, `tan`, `powf` — это `libm` конкретной платформы. Поэтому в допуске два
  числа: насколько может разойтись канал и какая доля пикселей может разойтись
  вообще. Эталонная сцена вдобавок обходится без `powf` (бликов нет) — чтобы
  ловить свои регрессии, а не округление чужой библиотеки.
* **Падение должно быть читаемым.** Рядом с эталоном появляются
  `scene.actual.png` и `scene.diff.png` (совпавшее — приглушённым, разошедшееся
  — пурпурным по величине расхождения), а в сообщении: сколько пикселей, на
  сколько и координаты первого. Совпавший прогон эти файлы убирает за собой.
* **Принять изменение — одна команда.** `RUNITY_UPDATE_GOLDEN=1 cargo test`,
  и в ревью видно ровно то, что поменялось на экране.
* **Детерминизм.** `headless::run` гоняет игру с фиксированным шагом, а не по
  часам, поэтому два прогона одной сборки дают одинаковые пиксели — это
  отдельный тест.

### 4.3. Чтение PNG: зачем понадобился inflate

Эталон нужно не только записать, но и прочитать, а записать его мог и другой
инструмент. Поэтому декодер полноценный: DEFLATE со stored-, fixed- и
dynamic-Huffman-блоками (RFC 1951) и 8-битный PNG — greyscale, RGB, палитра и
варианты с альфой, со всеми пятью фильтрами строк.

Проверяется это против настоящего zlib: в `tests/data/` лежат потоки, сжатые
питоновским `zlib`, и PNG-файлы, у которых каждая строка отфильтрована своим
фильтром — то, чего наш собственный энкодер никогда не производит. Плюс
round-trip своего энкодера через свой декодер (они написаны независимо друг от
друга). Заодно это даёт загрузку текстур из настоящих PNG.

## Часть 5. Побочные задачи, которые обычно и тянут зависимости

**PNG без `image`/`flate2`.** Запись и чтение здесь сильно разной цены. PNG
требует zlib-поток, но не требует, чтобы он что-то сжимал: deflate разрешает
«stored» блоки, поэтому энкодер — это CRC-32, Adler-32 и обрамление чанков,
около ста строк (`runity-render/src/png.rs`). Файлы выходят крупные, зато
формат настоящий. А вот читать приходится и чужие файлы, так что декодер
полноценный — см. §4.3.

**OBJ без `tobj`.** Текстовый формат, разбирается `split_whitespace()` за
шестьдесят строк, включая отрицательные индексы и триангуляцию веером.

**glTF без `gltf`.** Это тот формат, который стоит реализовать самому: JSON
плюс блоб вершинных данных, разложенных ровно так, как их хочет рендерер. Ни
оптимизации мешей, ни сжатия, ни философии графа сцены — читается за несколько
сотен строк, в отличие от FBX. Заодно понадобился свой JSON-парсер: строгий,
с ограничением глубины вложенности (десять тысяч открывающих скобок — это
переполнение стека у наивного рекурсивного разбора) и с объектами в виде
списка пар, потому что порядок обхода, меняющийся между запусками, — это
«детерминированный» пайплайн, выдающий два разных файла из одного входа.

**Математика без `glam`.** `Mat4` как четыре колонки `Vec4` — та же раскладка,
что у GLSL. Единственное место, где легко ошибиться, — инверсия матрицы; она
покрыта тестом на round-trip и на вырожденный случай.

## Часть 6. Симуляция: то, ради чего всё остальное

Рендерер показывает мир, но мир должен существовать и без него: развиваться,
пока никто не смотрит, одинаково на двух машинах и после загрузки сохранения.
Из этого следуют четыре решения, каждое из которых проще принять сразу, чем
переделывать потом.

### 6.1. Тик мира — не кадр

Кадр меряет, как быстро машина рисует; мир должен жить со своей скоростью.
`WorldClock` (`runity-core/src/clock.rs`) переводит реальные секунды в **целые
тики**:

```rust
clock.advance(frame_delta);          // накопить реальное время × скорость
while let Some(tick) = clock.next_tick() {
    world.advance_tick();            // системы работают тиками, не дельтами
}
```

Почему целые: две машины, прожившие одинаковое количество тиков, находятся
в одинаковом состоянии, а float-дельты такого не обещают никогда. Аккумулятор —
`f64`, иначе за десять минут накапливается заметный дрейф.

Отсюда же берётся всё остальное, чего ждут от стратегии: масштаб времени, пауза
(которая останавливает историю, а не прячет её), бюджет на догон — один зависший
кадр не должен обернуться попыткой посчитать пятьдесят тиков подряд, — и
`fast_forward`, который переводит «неделю отсутствия» в количество тиков, чтобы
мир досчитали пачкой, а не по одному. Календарь превращает тик в год, день,
время суток и сезон; `day_fraction` отдаётся прямо в небо и становится сменой
освещения.

### 6.2. Случайность, которую можно воспроизвести

`Rng` — PCG32 с именованными потоками: имя хешируется в номер потока, и
`Rng::named(seed, "combat")` не двигает `Rng::named(seed, "terrain")`. Это
не украшение: как только генераторы общие, добавление одного броска кубика
в бою меняет ландшафт, и воспроизвести баг становится невозможно.

Шумы (`runity-math/src/noise.rs`) сделаны на хеше координат, а не на
перетасованной таблице перестановок. Разница в том, что **порядок выборки
не важен**: чанк 700 можно сгенерировать раньше чанка 3, и он будет тем же
чанком. Значение в точке — чистая функция от `(seed, x, y)`, так что терраин
можно выбрасывать из памяти и пересчитывать когда угодно.

Состояние генератора сохраняется (`Rng::parts`), потому что сохранение, которое
восстанавливает мир, но не генераторы, — не сохранение: следующий бросок
отличается от того, который был бы, и дальше расходится всё.

### 6.3. ECS: запросы, события, изменения

Хранилище — по-прежнему поколенческие индексы и плотные массивы на тип
компонента. К ним добавлены три вещи, без которых симуляция не пишется.

**Запросы по нескольким компонентам.** `query2`, `query3`, `query_without` —
итераторы; `each2_mut`/`each3_mut` — замыкания. Разница вынужденная: выдать
одновременно `&mut A` и `&B` из одной `HashMap` безопасно нельзя, поэтому
хранилище на время итерации *изымается* из карты и возвращается в `Drop` —
в том числе если система паникует (это проверено тестом).

**Отслеживание изменений.** Каждый компонент помнит, когда появился и когда
последний раз менялся; мутабельный доступ идёт через `Mut<T>`, который ставит
отметку на первом `DerefMut`. Дальше `changed_since(tick)` — это ровно то, что
нужно отправить по сети:

```rust
for (entity, position) in world.changed_since::<Position>(acknowledged) {
    packet.write(&(entity, position));   // всё, чего вторая сторона не знает
}
```

Чтение отметку не ставит; `bypass_change_detection` есть для служебных полей,
за которыми никто не наблюдает.

**События с двойной буферизацией.** Отправленное становится читаемым на
следующем тике и живёт ровно один тик. Задержка намеренная: система, которая
реагирует на событие, должна видеть одно и то же независимо от того, запустилась
она раньше или позже отправителя. Порядконезависимость — это и есть
детерминизм. Удаление сущности шлёт `Despawned`, потому что отслеживание
изменений умеет сообщить об изменившемся компоненте, но не об исчезнувшем.

### 6.4. Один формат на сохранения, сеть и тесты

`runity-serialize` — little-endian, varint'ы на длины и небольшие числа, float'ы
битовым представлением, словари в отсортированном порядке ключей. Два свойства
делают всё остальное возможным:

* **Детерминированные байты.** Один и тот же мир кодируется одинаково всегда,
  поэтому сравнение двух снапшотов — `==` на срезе, а не обход графа.
* **Недоверие ко входу.** Каждое чтение возвращает `Result`: обрезанный файл,
  битый чанк или враждебный пакет дают ошибку с позицией, а не панику и не
  попытку выделить четыре гигабайта. Сорок тысяч фаззинг-кейсов в тестах
  проверяют именно это.

Заголовок `Archive` несёт магию, версию контейнера, тип полезной нагрузки и её
версию схемы, плюс CRC-32. `Reader` знает версию, которой мир был записан, и
`Deserialize` может по ней мигрировать — поле, добавленное в версии 2, читается
из старого сохранения как значение по умолчанию.

Derive-макроса нет: он потребовал бы proc-macro-крейта и, на практике, чужих
зависимостей. Вместо него `serializable!(Type { field, .. })` — на строку
длиннее атрибута, зато формат записан в одном месте и меняется видимой правкой,
а не как побочный эффект переименования поля.

### 6.5. Физика как часть симуляции, а не как эффект

`PhysicsWorld::step` (`runity-physics/src/world.rs`) идёт фиксированным
порядком: интегрирование скоростей → sweep and prune → точные контакты →
пробуждение спящих → warm-started импульсы → позиционный проход, чья
псевдоскорость снимается сразу после интегрирования → сон и запись импульсов
на следующий шаг. Каждый промежуточный список отсортирован — иначе порядок пар
зависел бы от порядка обхода `HashMap`, и две машины разошлись бы за секунды.

Контакты отдаются событиями, а не опросом: удар, начавшийся и закончившийся
внутри одного шага, иначе просто не виден. Пара, пропавшая потому, что оба тела
уснули, событием «разошлись» не считается — ящик не перестал лежать на полу
оттого, что его перестали считать.

### 6.6. Игрок — не твёрдое тело

Соблазн переиспользовать симуляцию для игрока велик, и он ошибочен. Твёрдое
тело двигают импульсы, а импульсы дают ровно то ощущение, которого в управлении
быть не должно: инерцию, которую игрок не задавал, отскок от ступеньки,
заваливание от касания ящика. Игрок, который борется с решателем, — это не
«реалистично», это баг-репорт.

`Character` (`runity-physics/src/character.rs`) — капсула, которая двигается
туда, куда сказали, и затем отказывается от той части движения, которую мир не
разрешает:

* горизонталь и вертикаль решаются **раздельно** — решённые вместе, стена
  превращается в пандус, и игрок лезет по стенам;
* при контакте из скорости вычитается составляющая в стену, а не вся скорость:
  скольжение вдоль стены — это то, из-за чего движение ощущается движением;
* шаг разбивается на подшаги не длиннее половины радиуса, иначе падение со
  скоростью 60 м/с проходит сквозь пол толщиной 20 см между двумя проверками;
* подъём на ступеньку сделан **пробами перекрытия**, а не выталкиванием: если
  подняться, шагнуть вперёд, опуститься и вытолкнуть капсулу из препятствия,
  её вышвырнет обратно — контакт внизу принадлежит боковой грани ступеньки,
  а не её верху.

Толчок динамических тел не зависит от их массы: импульс — это то, что может
приложить персонаж, а что с этим делать, решает само тело. Ящик уезжает,
валун почти не шевелится.

### 6.7. Управление: намерение, а не нажатие

Читать `Key::W` прямо в коде игры — самый дешёвый вариант ровно до того
момента, когда нужны переназначение клавиш, второе устройство ввода и сеть. Всё
решает третье. По сети нажатие послать нельзя: у второй машины другие бинды и,
возможно, другое устройство. Посылать надо то, чего игрок *хотел*.

Отсюда три слоя (`runity-core/src/action.rs`), и границы между ними — не
стилистика:

* `Bindings` — конфигурация: какие физические входы что значат. Сохраняется.
* `Actions` — состояние кадра, посчитанное из биндов и сырого ввода.
* `Intent` — то, что уезжает в сеть или в реплей.

**Действие — это хеш имени, а не индекс.** `Action::named("jump")` даёт одно и
то же число в любой сборке, поэтому сохранённая раскладка читается после того,
как в список добавили новое действие; индекс в списке при этом поехал бы.

**Фронт считается по истории действия, а не клавиши.** Разница видна на двух
случаях, и оба — реальные баг-репорты: действие на двух клавишах, одну
отпустили, вторая зажата (это не «отпустил», и не «нажал заново»); и
переназначение в меню на клавишу, которую игрок в этот момент держит (это не
нажатие). Поэтому `Actions` хранит прошлый кадр в терминах действий.

**Оси — целые, а не `f32`.** `Intent` пакует кнопки в битовое поле, а оси — в
`i16` в тысячных. Это вход в симуляцию, о которой две машины обязаны
договориться: ось, приехавшая как `0.7000001` там, где локально было `0.7`, —
это расхождение, которое проявится через минуту и будет выглядеть как «у него
персонаж стоит в другом месте». Квантование **в момент отправки** означает, что
обе стороны, включая отправителя, шагают ровно от того числа, которое
отправлено. Тысячные мельче, чем игрок способен почувствовать, и совпадают с
милли-единицами, которыми уже меряет стоимость поиск пути.

**Порядок задаёт `ActionSet`, а не бинды.** Битовое поле индексируется
позицией в наборе, и набор строится из списка в коде, одинакового у всех. У
набора есть `fingerprint`: две сборки с разными списками действий шлют друг
другу байты, которые значат разное, и это единственная ошибка здесь, которая
иначе вообще никак не проявляется — просто «он делает не то». Обменяться
отпечатком в рукопожатии стоит одно `u32`.

**Клавиши сериализуются стабильными кодами**, а не порядковым номером в
`enum Key`: добавление клавиши в середину перечисления не должно сдвигать
сохранённые настройки всем игрокам. Код, которого эта сборка не знает,
сохраняется обратно как есть — раскладка, записанная более новой версией, не
худеет при каждом запуске старой.

## Часть 7. ИИ: пространство, путь, решение

Между «мир существует» и «в нём кто-то живёт» лежит три задачи, и решать их
стоит именно в этом порядке.

### 7.1. Что рядом

Восприятие, расталкивание агентов, поиск ближайшего дерева, определение
региона, за который отвечает сервер, — это одна и та же задача, заданная
тысячи раз за тик. Наивный ответ квадратичен и проявляется ровно тогда, когда
деревня становится интересной.

`SpatialGrid` — равномерный хеш-грид по плоскости земли (высота сознательно
игнорируется: поселение растёт вширь, а третья ось утроила бы просматриваемые
ячейки). Он перестраивается целиком каждый тик, а не поддерживается по частям:
в симуляции почти всё движется, а устаревшая ячейка — это ошибка, которая
появится через час после написания кода.

Свойство, которое проверяет тест: грид может быть щедрым (вернуть лишнее из
соседней ячейки), но не имеет права пропустить то, что действительно рядом.
Проверяется перебором по всем объектам.

### 7.2. Как туда дойти

Земля для ИИ — `NavGrid`, байт на клетку. Байт не флаг, а множитель стоимости:
грязь, снег и крутой склон — это «пройти можно, но не хочется», и маршрут,
который это понимает, выглядит осмысленным, а не механическим.

Поиск — A* на **целых числах** (миллидолях клетки). Причина не в скорости:

```rust
// Так нельзя: у f32 нет полного порядка, ничьи разрешаются по-разному
BinaryHeap<(f32, u32)>
// Так можно: две машины вынимают узлы в одном и том же порядке
BinaryHeap<Reverse<(u32, u32)>>
```

На открытом поле ничьих больше, чем уникальных стоимостей, и если они
разрешаются по-разному, два клиента расходятся во мнении, где прошёл житель.

Три вещи, без которых A* в игре не работает:

* **Бюджет.** Маршрут в отрезанный угол карты без бюджета обходит весь мир —
  внутри тика, на каждый запрос. `PathError::Budget` возвращает управление,
  и вызывающий решает, искать ли дальше.
* **Запрет срезать углы.** Диагональ между двумя заблокированными клетками —
  это проход сквозь стык стен, и выглядит он ровно настолько неправильно,
  насколько является.
* **Вытягивание верёвки.** Маршрут по сетке — лестница; житель, идущий по
  лестнице, выглядит как житель, идущий по сетке. Проверка прямой видимости
  между опорными точками убирает лишние повороты.

Оптимальность проверяется не повторным запуском A*, а независимым полным
перебором (релаксация до неподвижной точки) на случайных картах.

Когда к одному амбару идут двести жителей, двести поисков по одной и той же
карте — это двести поисков по одной и той же карте. `FlowField` заливает сетку
от цели один раз и отвечает всем сразу. `next_step` возвращает центр следующей
клетки, а не направление: прямая между центрами двух клеток может задеть угол
стены, а точка-ориентир — нет.

### 7.3. Как идти и что замечать

Стиринг — то, чем агент отличается от интерполятора по точкам. `arrive`
тормозит перед целью (то, что стопорится мгновенно, читается как конечный
автомат), `separation` взвешивает ближайшего соседа сильнее всех, поэтому толпа
расходится, а не колеблется, а `avoid` реагирует только на то, что реально на
пути. Агенты, оказавшиеся ровно в одной точке, расходятся вдоль фиксированной
оси: случайное направление здесь — это рассинхронизация.

`PathFollower` хранит курсор по точкам маршрута. Курсор — это состояние агента,
а не то, что пересчитывается из геометрии каждый тик: пересчёт — стандартный
способ получить агента, вечно скачущего между двумя углами.

Восприятие вынесено отдельно от решений сознательно. Агент, который оценивает
варианты по истинному состоянию мира, всеведущ, и игрок замечает это мгновенно,
не умея сформулировать: монстр отвернулся раньше, чем мог бы увидеть. `Senses`
даёт конус, затухающий к краю, и слух, не зависящий от взгляда; `Awareness`
накапливает уверенность во времени, поэтому одного взгляда мало, а двух уже
достаточно — и у игрока есть окно, чтобы снова разорвать линию видимости.

### 7.4. Что делать дальше

Ни дерево поведения, ни конечный автомат: оба кодируют **порядок** решений, а у
жителя порядок меняется постоянно — голоден зимой, честолюбив весной, в ужасе,
когда появился монстр. Utility-оценка кодирует **причины**: каждый вариант
считает себе очки от состояния мира, побеждает лучший.

Соображения перемножаются, потому что одно невыполненное требование должно
обнулять вариант. Но перемножение слишком строго само по себе: четыре
соображения по 0.8 дают 0.41, и вариант, хороший во всём, проигрывает варианту
с одним посредственным соображением. Компенсация подтягивает произведение
обратно ровно на то, во что обошлось умножение, — это правка Дэйва Марка, и
без неё utility-ИИ не масштабируется дальше трёх соображений.

Ничьи всегда достаются более раннему варианту: порядок в списке — это заданный
приоритет, а не случайность. Там, где разнообразие нужно (сто жителей не должны
рубить одно дерево), `choose_near_best` выбирает среди почти равных, но из
именованного потока ГСЧ — толпа разная, прогон воспроизводимый.

## Часть 8. Сеть: что отправлять и кому верить

### 8.1. Почему UDP

Игре нужны два вида сообщений, и разница между ними принципиальная. Позиция
жителя должна быть **свежей**: потерялась — и хорошо, через 50 мс придёт
новая, а пересланная старая хуже, чем ничего. «Амбар достроен» должно
**дойти** — ровно один раз и в правильном порядке.

TCP умеет только второе и заставляет первое ждать за потерянным байтом. Это
head-of-line blocking, и это ровно та причина, по которой сетевой экшен на TCP
дёргается при каждой потере пакета.

Поэтому UDP плюс свой слой надёжности: подтверждения битовым полем на 32
пакета в каждом заголовке (потеря подтверждения ничего не стоит — следующий
пакет скажет то же самое), порядковые номера с учётом переполнения (16 бит —
это двадцать минут на 60 пакетов в секунду, и наивное сравнение убивает
соединение ровно в этот момент), фрагментация больших сообщений по упорядочённому
надёжному каналу.

`Connection` не знает о сокетах: байты на вход, байты на выход. Это не
архитектурная эстетика, а разница между «проверить надёжность на канале,
который теряет треть пакетов» и «проверить её на том, что сегодня сделал
loopback».

Два бага, которые нашёл тест фрагментации, стоят упоминания, потому что оба
структурные:

* Сообщение на 50 КБ — это 43 пакета. Пачка такого размера приходит с головой
  уже **за пределами** 32-пакетного окна подтверждений, где приёмник не может
  отличить новый пакет от уже виденного. Выбрасывать такие пакеты целиком —
  значит навсегда застопорить каждое фрагментированное сообщение на его же
  первом фрагменте. Теперь окно сообщает, какой именно это случай: надёжные
  сообщения дедуплицируются по собственным идентификаторам и обрабатываются,
  ненадёжные отбрасываются, чтобы не прийти дважды.
* Отправитель себя **ограничивает по темпу**: пачка шире окна — это патология,
  которую лучше не создавать.

### 8.2. Репликация: разница, а не состояние

Сервер держит мир, клиент — ту его часть, которая его касается. Поселение на
две тысячи сущностей — это мегабайты; то, что изменилось за десятую долю
секунды, — сотни байт. Отслеживание изменений уже знает разницу, поэтому вся
репликация — это `changed_since(acked_tick)`.

Отсюда же следует, почему чтение не должно ставить отметку об изменении: сервер,
который просто смотрит на свой мир (а он смотрит постоянно), иначе отправлял бы
его целиком каждый тик. Это проверено тестом.

Интерес — фильтр по сущностям — решает две задачи сразу: трафик и честность.
То, что не отправлено, нельзя вытащить из памяти клиента читом; «послать всё и
не показывать» — это не защита.

Каждое значение компонента длиннопрефиксировано, поэтому клиент старой версии
**пропускает** незнакомый тип, а не ломается. Без этого добавление компонента —
ломающее изменение для всех подключённых.

Дескрипторы сущностей на двух сторонах разные, и клиент держит отображение.
Считать их одинаковыми работает ровно до первого переподключения, а потом
ломается незаметно.

Удаления живут в журнале самого мира, а не в событиях: событие читается один
тик, а клиент легко отстаёт на три. Первая версия держала свой «могильник» и
требовала вызова каждый тик — это не API, это ловушка.

### 8.3. Разделённая авторитетность

Полностью авторитетный сервер решает конфликты тем, что решает всё сам, — ценой
задержки на каждое действие игрока. Разделённая авторитетность вместо этого
раздаёт владение: игрок владеет своим персонажем и тем, над чем работает,
сервер — остальным миром, включая медленную симуляцию поселения.

Два правила делают это безопасным:

* **Владение — аренда, а не подарок.** Она истекает. Клиент, упавший на замахе,
  не уносит дерево с собой: аренда кончается, и сервер забирает его обратно.
* **Ничьи решаются одинаково везде.** Две заявки на одном тике разрешаются по
  номеру пира, а не по тому, чей пакет пришёл первым: порядок прихода на разных
  машинах разный, номера пиров — нет.

Команды применяются в порядке (тик, пир, номер), а не в порядке прихода — по
той же причине. Команда «из будущего» отклоняется: её тик определяет, когда всё
происходит, и клиент, объявивший себя на тысячу тиков впереди, иначе
переупорядочил бы мир вокруг себя.

Чего здесь сознательно нет: проверки, что команда **осмысленна** — хватало ли
дерева, мог ли игрок дотянуться. Это правила игры, и сетевой слой, угадывающий
их, был бы и неправ, и в тягость. Нет и шифрования с аутентификацией: настоящему
развёртыванию нужно и то и другое, а самодельная схема была бы хуже честного
признания, что их нет.

## Часть 9. Предсказание и уровни детализации

### 9.1. Ходить сейчас, а не через сорок миллисекунд

На общем мире решает сервер, и сервер далеко. Клиент, который ждёт разрешения,
чтобы сделать шаг, ощущается как персонаж в патоке: задержка мала в
миллисекундах и огромна в ощущении.

`Prediction` (`runity-core/src/predict.rs`) делает три вещи:

1. применяет ввод **немедленно**, по тем же правилам, что и сервер;
2. хранит каждый применённый ввод вместе с полученным состоянием;
3. получив серверную версию тика `T`, сравнивает её со своим предсказанием для
   `T` — и если они расходятся сильнее допуска, откатывается к серверному
   состоянию и **переигрывает** все вводы после `T`.

Переигрывание — причина, по которой симуляция обязана быть детерминированной и
идти целыми тиками. Переигрывание с другим шагом или с обращением к общему ГСЧ
даёт другой ответ каждый раз и превращает каждую коррекцию в видимый рывок.

Допуск нужен потому, что две машины, считающие одно и то же в плавающей точке,
расходятся в последнем бите; коррекция на это означала бы коррекцию каждый тик.

Чего модуль сознательно не делает — не прячет коррекцию. Резкий скачок после
отката выглядит плохо, и лечится это подачей: рисуемая позиция подтягивается к
исправленной за несколько кадров. Это дело игры, а не движка.

### 9.2. Мир больше, чем машина

Премиса игры — поселение развивается, смотрит на него кто-нибудь или нет.
Буквально это означает симулировать всех жителей везде и всегда, что перестаёт
быть по карману примерно тогда, когда игра становится интересной.

Выход не в том, чтобы перестать считать дальние области, а в том, чтобы считать
их **грубо**. `Regions` делит мир на квадраты и держит для каждого уровень
детализации:

* **Full** — рядом наблюдатель, считается каждый тик, житель за жителем;
* **Coarse** — далеко, считается раз в N тиков и агрегатом;
* **Dormant** — никого рядом, не считается вовсе, только копит долг.

Ключевая деталь — не в самих уровнях, а в бухгалтерии: каждый регион, когда до
него доходит очередь, получает `elapsed` — сколько тиков он задолжал. Один
расчёт на пять минут отсутствия вместо пяти минут расчётов. Если забыть
отметить регион посчитанным (`mark_simulated`), тот же долг применится снова —
и деревня будет расти на неделю каждые десять секунд. Тест на это есть.

Регион, впервые увиденный на десятитысячном тике, не должен ничего: мир для него
начинается тогда, когда его впервые увидели, иначе каждый новый квадрат карты
мгновенно проживал бы всю историю мира.

И регионы, рядом с которыми давно никого не было, забываются — иначе карта
растёт на запись за каждый когда-либо посещённый квадрат.

## Часть 10. Анимация: скелет, поза, клип

Скиннинг — то место, где легко построить дерево объектов с `Rc<RefCell<..>>` и
обходить его рекурсивно каждый кадр. Здесь его нет: скелет — плоский `Vec<Joint>`,
родитель хранится как `Option<u16>` и **всегда** стоит в списке раньше ребёнка.

Это одно правило убирает половину задачи. Мировые матрицы считаются одним
проходом слева направо: к моменту, когда очередь доходит до сустава, матрица его
родителя уже посчитана и лежит в том же массиве. Ни рекурсии, ни стека обхода.

Но правило — наше, а не спецификации: glTF не требует, чтобы `joints` был
топологически упорядочен, и просто переставить суставы нельзя — индексы в
вершинах (`JOINTS_0`) указывают именно в этот массив. Поэтому `is_sorted`
проверяется перед проходом, и файл с ребёнком раньше родителя считается по
второму пути: предки разрешаются первыми, итеративно (глубокий скелет не должен
переполнять стек) и с остановкой на цикле, который битый файл вполне способен
описать. Медленнее — но «молча неправильная поза» хуже, чем «медленнее», и
разница видна только на файлах, которые иначе загрузились бы сломанными.

### 10.1. Три пространства, которые все путают

Сустав живёт сразу в трёх системах координат, и ошибка здесь даёт не панику, а
мешь, вывернутый наизнанку:

* **локальная** — поза относительно родителя, именно её меняет анимация;
* **мировая** — произведение локальных вверх по цепочке;
* **скиннинг** — мировая, умноженная на обратную bind-матрицу.

Последнее и есть весь смысл: обратная bind-матрица переводит вершину из
пространства модели в пространство сустава *в позе покоя*, а мировая матрица
возвращает её обратно уже в текущей позе. Отсюда свойство, на которое опирается
тест: **в позе покоя скиннинг-матрицы равны единичным**, и меш обязан совпасть с
исходным до бита. Если какой-то шаг перепутан местами, это видно сразу на
неподвижной модели, а не на середине анимации.

### 10.2. Клип — это каналы, а не кадры

Анимация хранится не как «поза на кадр N», а как набор независимых каналов:
сустав, вид данных (перенос, поворот, масштаб) и список ключей с временами.
Каналы разной длины и разной частоты — норма, ровно так это лежит в glTF.

Выборка ключа — двоичный поиск, а не линейный. Разница между `O(n)` и `O(log n)`
на клипе в десять ключей незаметна, но клип на тысячу — это по тысяче сравнений
на сустав на кадр, и деградация наступает не там, где её ищут. Между ключами —
`lerp` для переносов и масштаба, `slerp` для поворотов (`nlerp` по короткой дуге
экономит корень, но заметно «проваливает» середину на больших углах); режим
`Step` не интерполирует вовсе — он существует для дискретных вещей вроде смены
видимости.

Время заворачивается по длительности клипа, а длительность выводится из ключей,
а не берётся из файла: клип, у которого в заголовке одно, а в данных другое,
должен играть то, что в данных.

### 10.3. Смешивание и маски

`Pose::blend` — линейная интерполяция двух поз целиком; `blend_masked` делает то
же, но только для перечисленных суставов. Это минимум, на котором строится всё
остальное: бег ногами плюс замах руками — две позы и маска «всё от позвоночника
вверх», без третьего клипа и без специального кода в движке.

Чего движок сознательно не делает — не решает, *когда* переключать клипы. Граф
состояний, условия переходов, их длительности — это правила игры; движок даёт
позы и операцию их смешивания.

### 10.4. Что из этого читается из glTF

Загрузчик отдаёт скины и клипы в терминах узлов файла (`NodeAnimation`), а
`Model::animation_for(skin, animation)` переводит их в индексы суставов
конкретного скелета. Канал, указывающий на узел, которого в этом скелете нет,
отбрасывается, а не роняет загрузку: один файл часто содержит несколько скинов, и
клип персонажа не обязан ничего знать о скелете его лошади.

Веса из файла нормализуются при чтении. Экспортёры регулярно пишут сумму 0.999
или 1.002, и это те самые несколько процентов усадки меша, которые потом ищут в
шейдере.

## Что это стоит

Плата за отсутствие зависимостей — не в строках кода, а в том, чего нет:

* **Производительность.** Однопоточная растеризация; `cargo run --release
  --example bench` печатает цифры для машины, на которой запущен. На той, где
  это писалось, сцена уровня `showcase` в 640×360:

  | Что включено | Секунд на кадр |
  | --- | --- |
  | всё | 0.50 |
  | без SSAO | 0.34 |
  | без SSR | 0.38 |
  | без теней | 0.49 |
  | только геометрия и свет | 0.19 |
  | всё, 2× суперсэмплинг | 2.41 |

  То есть дороже всего — SSAO (24 отсчёта на пиксель с проекцией каждого) и
  SSR; тени почти бесплатны. Это сознательный выбор, а не долг: рендерер нужен
  для отладки и headless-прогона, а однопоточный проход проще читать и,
  главное, детерминирован — на этом держатся golden-тесты. Многопоточности и
  SIMD в планах нет; для интерактивной работы эффекты выключаются по одному
  (F1–F5 в примере).
* **Платформы.** Каждая стоит отдельного бэкенда: сейчас есть macOS, X11 и
  Win32, дальше — Wayland и мобильные. HiDPI на маке пока не включён.
* **Форматы данных.** glTF, FBX, шрифты, звук — всё это придётся писать
  самому, а спецификация glTF существенно больше OBJ. Из glTF читаются меши,
  материалы, иерархия узлов, скины и клипы; Draco, morph targets и расширения —
  нет.
* **Сеть.** Транспорт, репликация по интересу и разрешение конфликтов при
  разделённой авторитетности написаны (части 8–9), но проверены на
  симулированном канале и на localhost — не на реальной сети с NAT, потерями
  по пути и провайдером, роняющим UDP.
* **Эффекты, которых ещё нет.** Глубина резкости, motion blur, каскады теней
  для больших сцен, площадные источники света. И PNG-энкодер пока пишет
  несжатые блоки — полноценный deflate уменьшил бы файлы втрое.

Зато становится видно, из чего вообще состоит графика: ни один шаг конвейера
не спрятан за чужим API.
