# Импорт Unity-проекта

Карточка к пункту «Контент переезжает сам» из NEXT_STEPS.md и к постулату 8:
батарейка для любого, кто уходит с Unity, а первым — для Dacha Simulator
(51 сцена, 602 префаба, 151 материал, 105 Animator Controller, 270 FBX).

## Что делаем

`scrap import-unity <unity-проект> <scrap-проект>` переносит контент, а не
код: код игры переписывается руками (NEXT_STEPS, «Код и тесты»).

* **YAML Unity**: файл — это документы `--- !u!<класс> &<fileID>`, у
  каждого один ключ-тип (`GameObject`, `Transform`, `MeshFilter`…), ссылки
  — `{fileID, guid}`. Заголовки (тег `!u!`, `stripped`) читаем сами, тела
  — `yaml-rust2`. `fileID` — 64-битные: читаются целыми, не через `f64`.
  GUID ищется по `.meta` рядом с каждым ассетом.
* **Сцены и префабы** (`.unity`, `.prefab`) → RON со стабильными ID: ID
  сущности выводится из `fileID` GameObject, поэтому повторный импорт даёт те
  же ID и дифф показывает только изменившееся (постулат 2). Иерархия — по
  `Transform.m_Father`. Unity левосторонний, scrap правосторонний:
  зеркалим ось Z (позиция `(x, y, −z)`, поворот `(−x, −y, z, w)`).
* **Что на GameObject** → поля строки: `MeshFilter`+`MeshRenderer` →
  модель и материал (ссылки, docs/refs.md; встроенные меши Unity →
  `builtin:`), коллайдеры, `Rigidbody`, свет, камера, `AudioSource` →
  `sound:` (клип, громкость, высота, петля, играть при старте, 2D/3D по
  Spatial Blend, дистанции, группа микшера по имени). Выключенный
  GameObject (`m_IsActive: 0`) → `inactive: true`. Экземпляр префаба →
  `prefab:` с позицией, поворотом и именем из `m_Modifications`;
  `m_IsActive` и `m_Layer` частей — переопределения частей, в том числе
  частей вложенных префабов: Unity называет их `(экземпляр ^ источник) &
  i64::MAX`, импорт пересчитывает это в ключ scrap — ID экземпляра
  `within` ID части, как её называет вложенный префаб сам по себе.
  Сдвиг, поворот и масштаб части → её `transform` (несказанные оси — как
  в префабе), материал на рендерере части → её `material`, удалённые
  компоненты → `removed: ["light", …]` у части, добавленные к части —
  переопределение её компонентов. Объект, повешенный на часть экземпляра
  (его родитель — stripped-трансформ), → `in_part:` с ключом части.
  Части размещённой модели (FBX) — не сущности: их сдвиги в отчёте.
* **MonoBehaviour** → компонент игры текстом: имя — скрипт в snake_case,
  поля — RON из YAML. Ссылка на объект той же сцены становится
  `EntityRef`, на ассет — типизированной ссылкой. Код компонента пишется
  потом; до тех пор `check` называет компонент, которого нет в
  `src/components/`, — это и есть список работы.
* **Материалы URP Lit** (`.mat`) → `.scrmat`: цвет, metallic, smoothness,
  emission, прозрачность, отсечение, стороны, карты по ссылкам.
* **Animator Controller** → граф в `animators/` (`scrap::animgraph`):
  состояния, переходы с условиями, 1D-смешивание; клип по имени из
  `.meta` модели или `.anim`. Компонент Animator → `animator:` у строки.
* **Animation Clip** (`.anim`) → `clips/<name>.ron` (`scrap::motion`):
  кривые места, поворота (Эйлер) и масштаба по пути к вещи, `m_IsActive`,
  громкость звука, частота частиц; ключи линейно, касательные Unity не
  переносятся. Остальные кривые (материалы, цвет UI, свет) — в отчёте.
* **FBX** → glTF через Blender, если он установлен: `blender -b` с
  импортом FBX и экспортом GLB. Дальше модель идёт нашим путём glTF (меш,
  скин, клипы). Без Blender импорт называет модели, которые не перенёс.
* **Звуки и текстуры компонентов**: то, на что ссылаются сцены и
  префабы (не только материалы), копируется в проект. Звук — WAV, MP3,
  Ogg, FLAC; короче 10 с раскодируется при импорте, длиннее — хранится
  сжатым и играет потоком.
* **Отчёт**: что перенесено, что пропущено и почему — сводкой по видам
  (компоненты без аналога, поля модификаций, которые не перенеслись).

## Ответы постулатам

1. **Скорость итерации.** Импорт — одноразовая команда; повторный прогон
   перезаписывает то же самое, так что можно гонять до готовности.
2. **Git.** ID из `fileID` стабильны: повторный импорт после правки в Unity
   — дифф правки. Текст пишется как руками — строка на сущность.
3. **Модульность.** Импортёр живёт в `scrap-import` и в рантайм игры не
   линкуется; `yaml-rust2` — только там.
4. **Сеть.** Не касается.
5. **AI.** Команда CLI и отчёт текстом: агент гоняет импорт, читает отчёт и
   чинит по списку.
6. **Производительность.** Сотни сцен и префабов — секунды; FBX через
   Blender — минуты, по одному процессу на модель, только для изменившихся.
7. **Opinionated.** Один путь: Unity → RON-файлы проекта. Никакого
   «режима совместимости» с Unity в рантайме.
8. **Батарейки.** Для всех, кто уходит с Unity.

## Что принимаем как риск

* **Blender как конвертер FBX.** Внешняя программа, не наша. Свой разбор
  FBX — потом, если Blender станет мешать.
* **Модификации префабов** шире, чем позиция, поворот и имя, переносятся не
  все: отчёт их перечисляет.
* **Shader Graph и HLSL** не переносятся: это NEXT_STEPS «Свои шейдеры».

## Этапы

Сделано (2026-09-23): этапы 1–3. На Dacha Simulator: 50 сцен, 601 префаб,
151 материал, 24 текстуры, 105 графов за ~3 с; бинарная сцена
(`Mice.unity`) названа в отчёте. Ссылка компонента префаба на свою часть
в экземпляре переписывается под экземпляр (как в Unity) — это правка
раскрытия префабов в движке.

1. YAML, GUID, сцены и префабы с иерархией, трансформами, моделями,
   материалами, коллайдерами, телами, светом, камерой, MonoBehaviour.
2. Материалы URP Lit.
3. Animator Controller.
4. FBX через Blender.
5. Прогон по Dacha Simulator и отчёт.
