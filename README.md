# runity

Игровой движок.

Игрового кода здесь нет: движок проверяется на собственном — встроенных
мешах и материалах, примерах ассетов и примерах сцен. Дизайн игры, ради
которой всё затевалось, лежит в [docs/design/](docs/design/) — тринадцать
документов, от мира и поселенцев до экономики и того, как это выглядит. Они
задают, куда движок растёт.

## Принцип

Берём готовое. Своё пишем там, где упёрлись в потолок готового, а не заранее.

Так было не всегда: до этого движок собирался из одного `std`, без единой
сторонней зависимости — свой растеризатор, свой PNG, свой X11 по проводу.
Тот эксперимент закончен, и его код лежит в истории git. Чем именно его
заменили и почему — [docs/stack.md](docs/stack.md).

Чего мы хотим от движка и почему — [docs/DNA.md](docs/DNA.md): восемь
постулатов, от которых проектируется каждая фича.

## Раскладка

```
crates/runity          движок: сцена, ассеты, устройство, рендер, встроенное
crates/runity-cli      команда `runity`: new, sync, check
crates/runity-editor   сессия редактора: правки, отмена, гизмо, импорт, режим игры — без UI
crates/runity-mcp      тот же редактор как MCP-сервер: всё, что умеет редактор, умеет агент
crates/runity-import   импорт исходных форматов в формат движка (в игру не линкуется)
examples/valley/       проект-пример в стандартной раскладке: сцены, префабы, материалы,
                       модели и текстуры (Kenney, CC0) — на нём всё проверяется
docs/design/           дизайн игры, ради которой движок и делается
docs/DNA.md            восемь постулатов, от которых проектируется каждая фича
docs/stack.md          на чём и почему
```

## Проект

У любого проекта на runity одна раскладка — её знают все инструменты и
агенты, и её же пишет генератор:

```
cargo run -p runity-cli -- new ../moss --engine-path crates/runity
cd ../moss && cargo run      # окно на scenes/main.ron; сохранения сцены видны сразу
```


```
runity.ron   файл проекта: имя, версия движка
scenes/      сцены, RON — сущность на блок, `id` первым
prefabs/     префабы
materials/   .rmat — цвета в sRGB hex
assets/      исходники: модели, текстуры, звук
library/     собранные .rasset — производное, в git не попадает
Cargo.toml   крейт игры, свой workspace — правка игры не пересобирает движок
build.rs     находит компоненты и системы игры; руками не правится
src/main.rs  игра: окно и `step`, где системы идут по порядку
src/components/  компонент на файл; имя файла — имя компонента в сцене
src/systems/     система на файл
CLAUDE.md    что нужно знать агенту
```

Инструмент, которому дали сцену, сам находит её проект (ближайшая папка
вверх с `runity.ron`) и берёт оттуда префабы, материалы и библиотеку.

`runity add component door` пишет `src/components/door.rs`, и сцена сразу
может дать сущности `components: { "door": (…) }` — регистрацию делает
`build.rs` по имени файла, общего списка, который двое правили бы
одновременно, нет. `runity add system patrol` пишет систему и ставит её
вызов последним в `step`.

`runity check` говорит, что в проекте не сходится — модель, материал или
префаб, которых нет, повторившийся `id`, устаревший `.rimport`, — с файлом,
сущностью и ближайшим похожим именем. `runity sync` собирает `library/` из
исходников. `runity rename FROM TO` переименовывает или переносит ассет —
модель, текстуру, звук, материал, префаб — вместе с его `.rimport` и
переписывает каждую строку сцен и префабов, где было старое имя;
`runity uses FILE` показывает эти строки заранее. `runity assets` — все
ассеты проекта и сколько раз каждый использован, `runity delete` удаляет
только то, что никто не называет, `runity duplicate` копирует ассет как
новый.

## Редактор для агента

```
claude mcp add runity -- cargo run -q --release -p runity-mcp
```

`runity-mcp` — MCP-сервер поверх сессии редактора: открыть сцену или сделать
проект, дерево сцены, добавить и поменять сущность (одним шагом отмены),
удалить, дублировать, перепривязать, сделать префаб, отмена и повтор,
импорт, перезагрузка с диска, `check`, прогнать физику несколько секунд —
и `render`, который возвращает кадр PNG-картинкой, чтобы агент видел, что
сделал. В корне репозитория лежит `.mcp.json`, так что агент, открывший
репозиторий, получает его сам.

## Посмотреть на кадр

```
cargo run --release --example scene_shot -- examples/valley/scenes/first-light.ron -o frame.png
```

Референсная сцена открывается без библиотеки и без импорта — все модели в ней
встроенные, так что это самый короткий путь от `git clone` до картинки. В ней
земля, четыре дерева на разных дистанциях (туман), куб (полушарный ambient на
трёх гранях), сфера (нормали) и один неосвещаемый уголёк.

## Походить внутри

```
cargo run --release --features desktop-shell --example walk -- examples/valley/scenes/first-light.ron
```

WASD ходит, левая кнопка мыши крутит голову, Escape выходит. Сцену можно
править, не закрывая окна: сохранил файл сцены или префаба — через четверть
секунды правка в мире, а то, что успела сделать игра, на месте. Единственная
часть движка, которую CI не может выполнить — у раннера нет дисплея, — поэтому
она хотя бы проверяется типами отдельным шагом.

## Префабы

Вещь, собранная один раз, ставится много раз. Префаб — это одно поддерево
сущностей в своём файле (`examples/valley/prefabs/campfire.prefab`), а сцена
ссылается на него по имени:

```
(name: "west fire", model: "", prefab: "campfire", transform: (position: (-3.2, 0.0, 0.0)))
```

Экземпляр задаёт имя, место и, если надо, материал и физику корня; всё
остальное приходит из файла. Поправьте префаб — поменяются все экземпляры
сразу. Префабы лежат в `prefabs/` проекта: и `scene_shot`, и `walk`, и
редактор находят их через проект сцены, поэтому все трое показывают одно и то
же.

```
cargo run --release --example scene_shot -- examples/valley/scenes/camp.ron -o camp.png
```

Переопределений глубже корня пока нет — «у этого костра третий камень
повёрнут» не выразить. Это самая сложная часть системы префабов в Unity, и
делать её наугад хуже, чем не делать; когда понадобится — проектировать под
живую сцену.

## Кадр без видеокарты

Движок рисует на машине без дисплея и без графической карты — через
программный Vulkan. Это и есть то, на чём держатся CI, golden-кадры и любая
петля, где что-то меняется и надо посмотреть на результат.

```
cargo test --workspace
```

На Linux нужен программный драйвер: `sudo apt-get install mesa-vulkan-drivers`.
На macOS всегда есть Metal, на Windows — WARP. Если адаптера нет вообще, тест
говорит об этом одной строкой и пропускается.

## Ассеты

Ничего, что грузит игра, не является исходным форматом. Исходник импортируется
один раз, дальше движок открывает только своё:

```
cargo run -p runity-import -- examples/valley/assets/models/pine_large.obj --library examples/valley/library
cargo run --release --example scene_shot -- examples/valley/scenes/my-scene.ron
```

Понимает `.gltf`/`.glb` (то, чем экспортируют настоящие инструменты), `.obj`,
растровые картинки, `.wav` и `.rmat`. Узлы сцены glTF при этом обходятся: модель,
собранная из расставленных частей, остаётся собранной.

Материал — такой же ассет, как модель. `.rmat` — это цвет в sRGB-шестнадцатеричном
виде (`(color: "#697c55")`), перевод в линейное пространство делает импорт. Сцена
называет материал по имени, и это имя ищется сначала в библиотеке, потом среди
встроенных: один `#697c55` на весь проект вместо двадцати, разъезжающихся по
девятнадцати сценам. `builtin:stone` — если нужен именно встроенный.

```
cargo run -p runity-cli -- sync examples/valley
```

Библиотека (`library/`) производная и не коммитится: `sync` собирает её из
исходников. Рядом с каждым исходником лежит `.rimport` — путь относительно
проекта, хэш содержимого, ID ассета и настройки импорта, текстом. Он
коммитится, поэтому свежий клон собирает ту же библиотеку с теми же ID, а
переехавший файл находится по хэшу и сохраняет и настройки, и ID.
